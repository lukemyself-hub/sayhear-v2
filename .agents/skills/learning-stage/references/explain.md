# 讲解与理解

用于 Luke 需要先理解某个机制才能继续，或者 feature 的学习主线尚未讲过的时候。

## 先讲主线

Luke 还没有建立某个 feature 的整体理解时，先沿状态卡的学习主线讲一遍完整过程，例如一条用户输入如何组装成模型请求、回答如何保存、失败后如何恢复。标出每个部件的职责，以及本次议题在其中的位置，再进入具体议题。主线讲过之后，后续讨论直接引用，不重讲。

## 讲一个机制

- 先说学完能解释或判断什么。
- 讲清问题、机制和结果。一次一个概念，用产品实例或小图。术语首次解释后统一名称；类比按需使用，并说明局限。
- 结合当前代码、真实运行或标注示例，区分拟议设计和已运行的行为。讲机制，不列函数清单。
- 跨文件的运行机制用 `how`，设计依据用 `why`。
- 讲完说明它和当前议题的关系；有决定在等 Luke 回答时，回到那个决定。

## 观察理解

- 像同事讨论那样，用真实场景反问失败归属或方案取舍，不打分，不把问题称为测验。一次讲解最多问一个问题，不背诵、不反复打断。
- 按回应补讲，后续相关讨论再回访。
- 当场答对只是当次证据，可能只是短期熟练。没有回应记为未确认。讲过或写完笔记都不等于掌握。

## 记录

完整知识点结束时，按 [records.md](records.md) 写主题笔记和理解记录，阶段末整理索引。学习状态独立于设计、实现和验收。HTML 按需制作，不建立整套课程或 lesson 工作区。
