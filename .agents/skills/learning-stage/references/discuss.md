# 决策讨论

用于一个需要 Luke 做取舍或确认的议题。事实由 Agent 先查清，见 [investigate.md](investigate.md)；Luke 还不理解前提时，先按 [explain.md](explain.md) 讲解。

## 提出一个决定

- 先说这个决定在 feature 里的位置：它阻塞什么，定下后能解开哪些后续议题。
- 讲清问题、约束、证据、选项、推荐、代价和重评条件。选项通常是成熟主选和最强替代。
- 每次只问这一项。下游问题等这一项定下后，再判断是否仍需要问。

## 由谁决定

- Luke 决定产品体验取舍、阶段范围、关键架构、隐私与数据边界，以及难以逆转的选择。
- 符合已定原则的细节和可逆的常规整理，由 Agent 推荐，并在完整方案里说明，不单独提问。这些推荐同样写进 ADR 或 SPEC，Luke 审阅时可以推翻。

## 追问

Luke 的目标或偏好不清楚，或双方对取舍有分歧时，围绕这一个议题追问，直到能说清分歧在哪、各自理由和决策人。分歧澄清、Luke 作出选择或明确暂缓后，停止追问并回到 [focus.md](focus.md) 的主线。追问中出现的相邻问题按 focus.md 分流。

## 记录

- 写明接受、暂缓或拒绝，以及依据和适用条件。区分推荐、反方、暂缓、拒绝；未实测不写通过。
- 构建、开发、产品体验的决策点都建立或关联 ADR，格式和术语按 `domain-modeling`，但不采用它“只记录重要且难逆的取舍”的筛选规则。相关决策可合并，须逐项可追溯。未定的写为 Proposed 或草稿，列出选项和待确认项；达成共识后补全状态、决定、依据、取舍、重评条件，并更新 `docs/decisions.md` 索引。已澄清的术语更新 Glossary。
- 需要记录的决定不必都单独提问。
- 更新议题清单和状态卡，接续记录与 SPEC 链接 ADR。ADR 与学习笔记互不替代。
