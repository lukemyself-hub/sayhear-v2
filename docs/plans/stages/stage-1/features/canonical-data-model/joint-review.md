## 结论

四类主要记录的职责能对应既有行为，但不能把字段齐全视作设计全部收口。本轮补齐三项工程缺口，并明确 JSON 来源引用需要数据库校验。涉及删除、终态竞争和引用资格的跨模块边界继续保持未定，不自行选择或记为通过。

## 已补入草案的工程缺口

| 项目 | 原缺口与影响 | 草案补充 |
| --- | --- | --- |
| 幂等标识与不同意图 | 仅有 owner+client_request_id 唯一，无法说明相同 key 携带不同消息或目标时怎样处理 | 推荐服务端 request_fingerprint；相同意图复用，不同意图冲突拒绝，不追加 Provider 调用。具体错误映射与算法版本待 M4 |
| 首段与来源一致性 | assistant 建行、seq、run.output_attempt_id 和 attempt 首段观测分别保存，可留下有回答却无法明确来源的半套记录 | 作为同一次 owner/RLS 数据库操作保存，提交确认后再展示；幂等回查原消息，不新建替代行 |
| 可回看的准确耗时 | dispatch_started_at 是取得资格时刻，和真正调用网络之间存在提交等待；仅有时间戳不足以刷新后恢复准确观测 | 在 attempt 持久化首次正文与本地调用结束的单调耗时差；不把数据库收尾或 Provider 远端计费混入 |
| 输入 JSON 的引用约束 | attempt 自身 RLS 和表间外键不会自动验证 JSON 内的 source message IDs | 最终数据库设计须对来源存在性、同 owner、同会话实施不可绕过的校验；方式待输入 JSON/schema 定稿，读取仍按 owner 解析 |
| 尝试竞争 | 编号 1/2 不能单独阻止两次尝试同时处于活动状态 | 建议同一 run 至多一个 created/running attempt，备用创建同时检查主尝试已收口、run 仍活动与切换条件 |

以上为行为契约的工程细化，未逐项标为 Luke 新接受的产品决定，随完整规格审阅。也没有因为引用校验可能需要额外关系就擅自新增第五张产品表。

## 场景串联

| 场景 | 数据层应表达的关系 | 本轮状态 |
| --- | --- | --- |
| 正常发送并完成 | 用户消息/run/attempt 原子登记；输入+发送资格原子保存；首段+来源原子建立；正常结果与必要保存成功后 run succeeded | 契约与草案可对应，运行未验证 |
| 用户输入或输入记录保存失败 | 不调用 Provider；若数据库不能写，不能谎称失败终态已可靠保存 | 已有门槛，恢复细节归 M4 |
| 首段前主路线错误，备用成功 | 主 attempt 先收口，再创建第二次；输出明确关联备用；run 最终 succeeded | 关系可对应，竞争条件归 M4 |
| 首段保存提交失败或应答丢失 | 不先展示；查证是否已建立原消息与来源；不得因尚未显示而 fallback 或重复建行 | 已补工程要求，需受控验证 |
| Provider 正常结束但最终保存失败 | attempt 可 succeeded，run 不得 succeeded；保留此前已落库内容 | 已有状态分工，消息最终状态与失败优先级归 M4 |
| 首段前主动停止 | run interrupted；若确认未发送，attempt finished/not_sent；无空 assistant | 已接受，运行未验证 |
| 首段后主动停止 | 保留已保存部分回答、输出来源；run interrupted；attempt 无可靠远端终态时 unknown | 已接受，取消与保存竞态归 M4 |
| 发送资格保存后进程消失 | running 不是远端送达证明；超期恢复收口，不自动重放；Provider 结果无法确认则 unknown | 已接受，期限与恢复竞争归 M4 |
| 同一 key 并发重发或换内容 | 相同意图不重复；不同意图拒绝，不能静默把另一条消息当作原请求 | 本轮补充工程草案 |
| 旧输入来源删除后回看 | 保留消息 ID 与缺失位置，不显示被删原文；其他当次信息按旧版本读 | 已接受，来源解析校验待输入 JSON 定稿 |
| 删除正在生成的 assistant 消息 | Luke 澄清目标界面只提供停止，没有该删除入口；停止保留部分回答 | 撤回当前必决问题，不增入口；M5/M7 明确需求时重访，未验证 API 或竞态 |
| 已结束消息格式迁移 | 旧输入引用不改变含义，不把新 parts 位置或新版 SDK 结果冒充旧输入 | 已登记要求，实际升级出现时设计，不预建通用框架 |

## 尚不能关闭的事项

M2 自身还需完成输入引用 JSON、不可绕过的 source 校验方式、具体 seq 分配与合并约束及格式版本的实际合同。字段名和可推导统计不逐项产品表决，但完整方案须可审阅并覆盖真实约束。

M3 负责部分/变化中消息与裁剪、时间表达；M4 负责终态竞争、恢复期限、checkpoint、备用与取消；M5 负责迟到消息合并及保存错误展示；M6 负责 usage/模型/耗时来源；M7 负责删除生效顺序。转交归属不等于这些边界可以在实现前不决定。

后续范围校准：Luke 澄清生成中界面提供停止按钮，没有删除正在生成的回答选项。主 Agent 将未进入界面范围的场景升级为必决问题不合适，已撤回，不新增入口；该问题仅在 M5/M7 以后明确允许的操作需要时重访。当前回到 M2 的输入引用 JSON 与数据库来源约束。

此前“删除即停止”的推荐未获接受，暂缓保留这一讨论经过。当前停止按钮沿用已接受规则：停止当次生成，不 fallback，保留已保存部分回答并标记中断，不将停止自动当成删除。
