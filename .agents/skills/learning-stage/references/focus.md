# Feature 焦点

## 阶段计划

阶段 `plan.md` 列出全部 feature（计划中的模块即 feature）、依赖、决策点、学习目标和验收，格式见 [records.md](records.md)。深入任何 feature 前，计划须存在并经 Luke 确认。新发现更新计划；影响阶段范围的变化须 Luke 确认。

恢复时缺少总计划、总接续或当前 feature 的状态卡，先根据权威任务、ADR 和已有局部记录补出最小可用版本，标注补录日期、来源和未知，再选议题。最小可用版本是：`plan.md` 列出各 feature、来源和状态；总接续写明当前 feature 和下一动作；当前 feature 有完整状态卡和议题清单。不要直接从局部记录里的“下一个问题”接着问。

## 状态卡

每个活跃 feature 的接续记录顶部保留状态卡。有 `features/<slug>/session.md` 时写在那里，小 feature 写在阶段 `session.md` 的对应段落。

| 字段 | 回答 |
| --- | --- |
| 目标与边界 | 提供什么能力；哪些内容由其他 feature 负责 |
| 完成条件 | 设计收口需要明确的行为、边界、契约和验收 |
| 学习主线 | 贯穿本 feature 的一个真实场景，以及 Luke 学完能解释或判断什么 |
| 当前停点 | 上次停在哪；已定、候选、未确认的内容 |
| 本次目标 | 本次推进到哪里，为什么先做这一段 |

状态卡只写摘要，详情链接 ADR、证据和讨论历史。
状态卡和议题清单可以用表格，也可以用等价的分节，只要字段齐全。

## 议题清单

紧跟状态卡，一项一行：

| 议题 | 类型 | 阻塞本次目标 | 状态与当前结论 | 下一动作 | 依据 |
| --- | --- | --- | --- | --- | --- |

- 类型：决策、事实、理解、依赖。
- 状态：待处理、有推荐待确认、已接受、暂缓（写重访条件）、转交给某个 feature。

## 分流

新问题先判断归属和影响，再决定是否现在处理：

- 阻塞本次目标：列入清单，按类型处理。
- 事实未知：Agent 去查，不问 Luke。
- 理解缺口：先讲解。
- 属于其他 feature：转交，在两边登记依赖和讨论入口，本 feature 不展开。
- 不阻塞本次目标：暂缓，写明重访条件。
- 已接受的决定：只有出现新证据或前提变化才重开，重开时说明变化。

分流结果向 Luke 说一句即可。

Luke 主动提出的新问题同样先分流。若当前还有一个决定在等 Luke 回答，先说明新问题和它的关系：不阻塞时简短回答或登记，可以附上推荐，但不另提要 Luke 回答的问题，然后回到等待中的决定；阻塞或 Luke 明确要先谈它时，把等待中的决定标为暂停并登记，再处理新问题。同一时间只留一个待 Luke 回答的决定。

选下一项时，优先阻塞本次目标且前置已满足的议题；有多项时，选定下来后能解开最多后续议题的那项。一次只处理一项。

## 收口

- 设计收口：完成条件逐项满足；必决议题都已接受，或经 Luke 同意暂缓、转交。
- 学习收口按 [explain.md](explain.md) 单独记录。理解缺口只有在影响仍待确认的关键选择时，才阻塞设计收口；其余记为回访。

收口时更新 `plan.md` 状态，报告已定事项、遗留议题、阶段剩余 feature 和下一步。feature 收口不等于阶段收口，可以整理局部草稿。

## 更新时机

启动、议题状态变化、feature 切换、暂停和收尾时更新状态卡和议题清单。讲完一个小概念不触发文档整理。暂停或上下文将满时，先保存停点和下一动作。
