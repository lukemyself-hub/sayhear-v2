# SayHear 功能搭建与学习计划

状态为 Proposed，技术路线与阶段启动决定仍待讨论。Luke 已确认阶段划分与顺序、学习覆盖，并接受时间预算作为随学习过程调整的估算。阶段 1 若超过 25 小时，可适度延长并按需使用 15 小时共用缓冲。计划以 [CONTEXT.md](../../../CONTEXT.md) 的 2026-10-20 共识为准。研究推荐不等于已接受选型。本文描述阶段目标、功能规格边界、验收与学习路线，具体 schema、接口、检索策略和任务调度在阶段启动时再研究。

目标是在 2026-12-31 前，做出 Luke 愿意日常使用、能解释关键机制的文本 Agent。长期继续成为供真实用户使用、可维护的多用户产品，让日常经历被听懂、被记住，并留下连续的人生记录。后台 Agent 工作不计入 Luke 每周约 10 小时，讨论、阅读、体验、讲解和笔记均计入。

## 阅读和执行本计划

会话交接。阶段划分、学习覆盖和初始预算已获 Luke 确认，技术路线仍在讨论，阶段 0 尚未正式开展。下个会话从阶段 0 开始，选定主线并明确边界。阶段 0 验收通过后才进入阶段 1，建立基础对话与 canonical 闭环。AI SDK 保持有条件优先，具体选型和数据边界在实现前形成共识与 ADR。提交计划不代表接受全部推荐，也不代表任何阶段已通过。

每阶段启动时，先看上阶段结果与未解问题，再围绕本阶段进行专项调查，形成 working spec，讨论关键架构与体验选择。达成的技术决定写 ADR，术语只在真正澄清后更新 GLOSSARY。执行沿用仓库规范，不因本计划自动授权提交、推送、部署或对外开放。

每阶段结束同时检查真实行为、实际体验和 Luke 的理解。验收记录必须链接运行、回放、数据或体验反馈。计划中的验收项都尚未执行，不能当作测试结果。阶段之间允许重访问题，不以周数或笔记完成度代替通过。

研究比较与来源集中在 [技术路线与产品研究依据](sayhear-route-research.md)。本文维护推荐路线、阶段和待确认问题，避免同一决定散在多份文档。

## 推荐的技术路线

推荐采用 TypeScript Web 主线，复用旧 Portal 的聊天体验，部署到 Vercel。以 AI SDK 为优先 Harness 基础候选，Mastra 为主要替代。优先使用成熟 SDK 的模型、流式和工具循环能力，SayHear 负责自己的上下文政策、canonical 数据语义、人格与记忆使用规则。

这项推荐依据当前以文本聊天、输入可解释和 Provider 替换为主的需求，不代表 AI SDK 已被证明优于 Mastra。首阶段核对两者对真实 Provider、实际输入查看、取消、工具与存储归属的支持。若 Mastra 能减少明确的接线与维护工作，且不产生重复状态和来源盲区，可改选 Mastra。若文档已能解决差异，不做重复原型；只对影响选择的剩余未知安排同场景有限验证。Luke 参与不超过约 4 小时，计入阶段 0，不另开框架竞赛。

两者不是互斥的底层路线。Mastra 接受 AI SDK 的模型对象，也能经适配层使用 AI SDK 的聊天 UI。要决定的是执行循环、上下文组织与工具编排由谁负责，以及记忆、工作流和观测采用现成框架能力还是自行连接。Luke 已形成的判断是，AI SDK 更便于显式观察编排层和消息流的每个环节，适合作为理解 Harness 内部结构的起点；Mastra 集成度更高，自带记忆、工作流与观测，采用其成套能力时可能减少开发量。这两个方向都不预设最终选型。

选型不比较功能清单长短，用四个可核验的问题判断。canonical 数据的归属是否清楚，能否导出、删除和重建。一次运行发送了什么、为什么选这些历史，是否可观察。采用的内置记忆能否区分用户表达与 AI 推断，能否处理失效和清理。Reflection 的执行、失败、补跑和恢复，是复用框架能力还是需要另建。若 Mastra 在这四点上明显更好且确实减少实际工作，则改选 Mastra，已采用的 AI SDK UI 可继续保留。

Reflection 是否复用框架能力不从技术偏好决定，按产品需求和教学两个角度判断。产品角度是能否保留依据、区分用户表达与 AI 推断、识别时间变化，并用后续对话验证作用。教学角度是能否解释输入范围、处理链路、产物使用与失效，以及重复触发为何不重复生效。两角度都不预设倾向，阶段 4 启动时按实际候选比较。

推荐一个托管 Postgres 保存 canonical 数据，Supabase 与 Neon 在阶段 0 比较后选一项。测试库与用户库使用独立实例和凭据。先构造可解释的基础记忆，再按失败场景决定是否采用 Mem0、Honcho、Hindsight 等组件。Zep、Graphiti 和 Letta 也保留适用条件，不把图谱或状态化运行时列为默认前提。

运行详情首先服务于理解一次真实对话。第三方 tracing 与评测服务按实际需要添加，不能代替产品内运行详情。Reflection 先以线上可触发、可回看、可补跑的处理闭环证明价值，再决定是否加入 Workflow、Inngest 等耐久执行或定时调度。后台执行不得依赖开发电脑或浏览器持续打开。

Provider 只先选一条实际可用主路径，之后用第二条验证替换。OpenCode、DeepSeek、WorkBuddy 的名称不等于已确认协议。接入前核实具体服务、可用模型、授权、内容去向，以及流式、工具、结构化产物、停止和错误差异。密钥不进入仓库或研究材料。

## 哪些结论可以确定

以下边界来自现有共识，当前计划不重新打开。

- 先基础对话和 canonical 数据，再逐步加入人格、基础记忆和 Reflection。
- 年底覆盖模型调用、流式、工具、停止、失败、可替换 Provider、运行详情、测试数据与 Vercel 聊天。
- 原始表达、AI 产物与来源关系清楚。用户自述不等于外部核验事实，AI 推断不能冒充用户原话。
- 真实用户库与测试库隔离，私人对话不得自动进入测试集或仓库。
- 初期具备基本访问控制、内容查看与清理，归属和访问设计兼容未来多用户。
- 稳定人格倾听优先，有好奇心、共情与独立判断，保持非人身份和关系边界。
- 日记、完整纠正与遗忘、Open Loop、实时语音和完整多用户系统在后续推进。

以下是本轮研究的较强工程结论，仍需在采用方案时检查如何落实。

- 模型 SDK、持久编排、记忆服务与数据库分属不同职责，不能把其中一项当作全部产品能力。
- 采用框架不免除数据归属、来源、权限、删除与质量评测责任。
- 官方接口存在不等于实际 Provider 等价。厂商基准不等于 SayHear 体验。
- 学习应围绕真实请求、状态与产物展开。理解机制不要求从零重写成熟 SDK。

## 阶段 0 选定主线并明确边界

目标是让 Luke 理解候选层级与取舍，选定一个可持续推进的主线。阶段结束后可以开始实现，无需继续大范围横评。

### Feature & spec

- 核实首个 Provider 的实际服务、协议、权限和数据去向，明确退路。
- 完成 AI SDK 与 Mastra 的同一组能力判断，覆盖 Provider 接入、流式、取消、工具循环、持久化归属与可观测性。只对资料无法回答的阻断点做有限验证。无法确认的项标为 unknown，不用一方较少的证据代替比较。若两者都不满足，退路顺序是自建薄循环加 SDK 原语，由 Luke 与主 Agent 决定，不临时重开大范围横评。
- 确定第二 Provider 的可用性与退路。若无第二个真实 Provider，用本地或 mock 适配器验证抽象边界，并在验收中标注这不是真实替换。
- 选定数据库与基础访问方式，明确测试与用户库隔离、地区、备份及费用边界。
- 确认旧 Portal 复用的布局和交互，以及旧事件、会话、鉴权和运行详情需适配的部分。
- 形成首个真实闭环的 working spec，不先决定完整 schema、向量库、图谱或画像类型。明确每个外部服务的默认遥测发送什么、能否关闭，以及 Vercel 函数时长、流式与取消传播、冷启动等平台限制。
- 定义合成数据集的编写与校验责任，列出最低覆盖清单，包括多日交流、人物关系、偏好变化、否定、同名人物、无答案场景、无关敏感细节和恶意历史指令。数据集与记忆实现分开估算，避免阶段 3 因数据未就绪而滑期。

### 验收标准

Luke 与主 Agent 能用同一条请求说明浏览器、Harness、Provider、数据库与可选服务各负责什么。记录采用路线和不采用其他路线的理由，列出实测尚未完成的能力。明确首阶段访问者、内容去向与清理方式。重要选择获得共识后才进入实现，未决定项有所在阶段和负责人。

### 学习活动与理解证据

用一个真实或合成请求示范输入、调用、流输出与保存。保存部分可以是一次性脚本或 Provider 控制台观察，不做产品持久化，时间盒不超过约 1 小时。完整持久化路径属于阶段 1。Luke 用自己的话说明为什么 SDK、数据库和记忆不是一回事，并解释选择方案会把什么责任留给 SayHear。几天后在另一个场景重访该判断，不要求背术语。

### 待确认问题

首个 Provider 与可支出预算是什么。初期真实访问是否仅 Luke。数据区域和外部遥测边界如何设定。AI SDK 与 Mastra 的采用理由是否符合 Luke 的理解与维护偏好。旧 UI 中会话与日期导航哪些是必须保留的体验。

## 阶段 1 建立基础对话与 canonical 闭环

目标是尽早得到能随时打开使用、出错时知道发生什么的文本聊天。canonical 数据从这个阶段开始，避免记忆和人格建立在不清楚的消息保存方式上。这个阶段同时承载运行链路与部署、清理、测试库和验收格式等边界契约，工作量在六阶段中最重，25 小时偏紧。若到本阶段中段发现不足，先用缓冲并记录超支原因，再与 Luke 讨论把数据装载与恢复或部署门禁的一部分移到阶段 0，不静默压缩验收项。

### Feature & spec

- 复用聊天布局、消息展示、输入、流式反馈与响应式交互，按 v2 契约适配。
- 接入主 Provider，实现流式、停止、超时与失败状态，以及有界重试。
- 保存原始输入、生成内容与来源关系，重新打开仍能查看历史。取消和半截输出有明确状态。
- 运行详情的最小版本能查看实际模型输入、所选历史、模型与失败位置，不展示未获得的内部推理。
- 建立合成数据装载与恢复方式、两个隔离数据库、基本访问控制、内容查看和清理。
- 从开始就标明数据归属，使用合成主体检查访问边界。完整账号管理暂不展开，但合成主体需要可辨识的测试身份，否则隔离测试无法执行。
- 在真实 Provider 闭环记录首段可见输出等待、完成时间、失败与单次成本，保留模型、输入规模和网络条件作为后续比较基线。阶段 2 共同确定可接受目标，阶段 3 与阶段 4 在同类场景检查新增机制的代价。
- 定义清理契约。初期最低做到单条清理与整个账户清理，清理后的内容不得进入当前上下文。产品日志、平台日志、备份和 Provider 侧内容可能仍在，限制范围写清楚，不把删除主记录说成彻底消失。完整删除与纠正流程仍留后续阶段。
- 建立测试库护栏。测试运行拒绝连接非测试实例，测试环境不注入生产凭据，并做一次故意交叉连接验证，确认失败且没有触及用户库。
- 配置 Vercel 项目、环境变量与密钥，从干净环境做一次部署 smoke test。仓库与日志中不出现密钥。
- 部署保持私密。未认证请求被拒绝，在访问控制与年龄、危机边界获批前，生产 URL 不可公开访问。用一次未认证请求验证并记录结果。
- 定义验收证据记录格式，字段包括场景编号、输入、期望行为、实际输出或运行链接、模型与 prompt、persona、上下文策略版本、数据集版本、结论与 commit。新运行可按记录回放。执行方式是脚本还是手动在本阶段确定。
- canonical 语义上容纳用户输入、生成内容、系统与人设指令、工具调用、工具结果，以及后续派生和 Reflection 产物的位置。本阶段不固定存储形状，但一条合成的系统消息和一条合成的工具调用要能保存、检索并在运行详情中显示，避免阶段 2 被迫迁移。

### 验收标准

在开发电脑离线时，Luke 能通过 Vercel 部署版聊天。刷新与重开不会丢失已完成历史。流中断、取消、重试与 Provider 故障不会伪装成成功或产生难以解释的重复历史。实际输入与保存结果可沿来源追踪。测试重置只作用于测试实例，合成主体不能读取彼此内容。私人原文不出现在仓库、测试集或未经决定的外部追踪中。清理后的内容不会继续被当前上下文选用。

### 学习活动与理解证据

沿一次真实运行查看浏览器请求、服务端上下文、Provider 输出和保存结果。Luke 能解释 UI 消息、模型消息与 canonical 数据为什么不一定同形，指出停止发生在网络、模型还是保存层。围绕真实实现改一项小行为并观察结果，由主 Agent 提供必要引导。

### 待确认问题

取消后的部分内容怎样显示和保存。历史如何分组、跨日怎样展示。初期清理做到单条、整段还是整个账户，派生产物如何失效。登录与访问方式是什么。Provider 报错如何显示才不影响聊天体验。

## 阶段 2 完善人格、上下文与 Harness

目标是先让“被听懂”成立，同时补齐可解释的工具循环、上下文预算与 Provider 替换。

### Feature & spec

- 建立稳定非人类人格，倾听优先、自然好奇、尊重停止、不盲目附和、不虚构经历。
- 明确上下文来源与预算，长对话的历史选择或压缩可以展开说明。
- 使用一个低风险、可解释的工具场景验证模型请求工具、执行、结果回传与停止上限。
- 通过第二个实际 Provider 验证调用边界，显式处理能力差异与不支持状态。
- 扩展运行详情，覆盖工具输入结果、步骤与结束原因。建立小型人格与 Harness 行为集。

### 验收标准

场景覆盖情绪表达、明确不想要建议、反复追问、错误自我判断、未知事实、身份询问与直接任务。每类先写下期望行为和不希望的行为，Luke 对一组具体回复逐例确认。明确不想要建议却仍给计划、虚构人类或离线经历、用依赖或排他的话术挽留，属于类别级失败，不通过本阶段。工具结果不能升级为系统指令，故障不会无限循环，场景包含工具结果中含指令的对抗案例。更换 Provider 后历史和产品语义仍成立，不支持的功能明确失败或采用已说明的退路。长历史的选入与排除理由可查，不能把摘要默认为原话。

### 学习活动与理解证据

对同一场景查看不同人格或上下文配置，解释行为差异来自哪里。Luke 能沿真实工具回合说明谁决定调用、谁执行、结果怎样回到模型；能区分人格不合适、历史遗漏、工具失败和 Provider 差异。后续记忆阶段再重访上下文预算。

### 待确认问题

哪些回复例子体现 Luke 要的温暖、敏锐与独立判断。追问怎样才自然，不能仅以固定问题数替代体验判断。工具的最小用途是什么。可接受的等待体验、成本和降级方式是什么。年龄与危机响应边界如何表述，尤其是未来对外开放前。

## 阶段 3 建立基础记忆与跨日连续性

目标是隔天不必反复重讲重要背景，同时避免错记、过时引用和令人不适的提起。

### Feature & spec

- 从 canonical 数据派生少量有来源的可召回内容，区分用户表达、转述与 AI 推断。
- 构造跨日历史和按需检索，保留近期上下文的简单对照。
- 覆盖人物关系、时间变化、否定、偏好更新和无相关记忆时的行为。
- 场景按四类失败生成。不知道只看到局部历史、该联想时没有查询、查询了但措辞不匹配、找到旧状态却漏了最新状态。前三类已有场景覆盖相近内容，第四类要求新证据能压过旧证据，第一类要求模型说明自己只看到某个范围，不冒充完整历史。
- 运行详情可查召回了什么、来自哪里、为何带入，并显示派生步骤，包括源消息、抽取方式和版本。用户可查看并基本清理。
- 依据主要失败类型挑选至多一个外部记忆候选比较。事实抽取检索、用户建模和时间关系分别有不同适配对象，不提前指定冠军。比较时用同一批场景和相同上下文预算，四问作为通过或停止判据。内容来自哪里，表达者是谁，什么时候成立，本轮回复为什么选中它。

### 验收标准

版本化合成数据包含多日交流、足量背景、清晰人物关系和前后变化，可重复装载恢复。数据集在阶段 0 已确定编写责任和覆盖清单，阶段 3 只做补充校验。相同场景比较无记忆与有记忆版本，分别记录准确性、自然程度和代价，证据按阶段 1 的记录格式保存。覆盖同名人物、他人经历、改变偏好、未知答案、无关敏感细节和恶意历史指令。跨用户泄漏、无依据断言、把 AI 推断当原话、把已失效内容当当前事实均不能被平均分抵消。清理后旧派生产物不再进入当前召回，重新构建也不能复活已清理内容。派生内容的来源能沿运行详情回到原话。完整用户纠正与遗忘流程仍留后续，但初期查看和清理范围在此阶段写清楚。

### 学习活动与理解证据

Luke 沿“原话、派生、检索、注入、回答”追踪一次记对与一次记错，判断故障在哪一步。比较召回命中与回答合适的区别。隔几天换一个人物或时间场景再次判断，记录需要引导之处，不以一次复述认定掌握。

### 待确认问题

哪些事情值得记，哪些只用于当下。敏感内容是否默认进入长期记忆。怎样提起才感到被记住而非被监视。基础记忆范围怎样与 Reflection 分工。外部组件的收益是否值得新增存储、调用和删除责任。

## 阶段 4 建立 Reflection 与画像更新

目标是对历史形成有依据、可修正的观察，并用后续对话证明它的作用。

### Feature & spec

- 先处理明确范围的一段历史，保存输入范围、生成时间、依据与状态。
- 区分明确表达的经历和观点、AI 观察与推断、随时间更新的画像。
- 明确执行模型。若同步处理，写清最大输入范围、超时与失败行为；若需要跨重启恢复，采用最小 job 记录加 worker，不默认引入第三方任务平台。执行模型与超时、重试和去重行为写入本阶段验收。
- 后续上下文能有选择地使用结果，失败或不确定产物不自动冒充有效结论。
- 针对无新内容、重复任务、处理失败、画像矛盾和来源清理处理生效边界。
- 运行详情和用户可见面能显示一条 Reflection 被哪些回合使用、为何失效，派生来源能回到原话。最低用户可见范围在本阶段确定，完整控制面仍留后续。

### 验收标准

同一段历史可解释得到哪些观察，关键结论能回到依据。新表达能推动重新判断，不把用户固化为标签或心理诊断。重复触发不会重复生效，失败可定位补跑，清理来源后旧结果不再继续生效。对照展示 Reflection 改变了哪些输入和后续回应，同时检查是否增加误解。措辞漂亮或任务成功不等于理解正确。两个合成主体的 Reflection 与画像产物不能互相泄漏，恶意或错误历史不得变成画像断言。线上执行离开开发电脑后仍能完成任务并按既定的超时、重试与去重行为处理。

### 学习活动与理解证据

Luke 解释一次 Reflection 的输入、处理、产物、使用与失效链路，说明后台处理为什么不同于实时回复，为什么重试仍需要考虑重复写入。比较一条有依据观察与过度推断，并在后续新对话中确认判断是否仍成立。

### 待确认问题

`fact`、`opinion`、`profile` 的实际含义与关系是什么。哪些观察可默认用于对话，哪些需确认。处理范围、触发节奏、过期和更新怎样决定。是否需要耐久任务平台，以及产物没有改善体验时怎样收缩机制。

## 阶段 5 收敛日常使用并整合理解

目标是验证整个文本产品可一起工作，明确可靠和不可靠的范围。

### Feature & spec

- 进入持续数天的日常使用，集中修复阻碍聊天、错记与错误恢复的问题。
- 回归关键合成场景，检查 Provider 替换、来源、隔离、清理、任务失败与恢复。
- 汇总从阶段 1 持续记录的响应等待、错误和成本基线，按阶段讨论的目标判断是否可接受。
- 整理工程入口、运行说明、已知限制和下一阶段建议，不新增大功能。

### 验收标准

完成一次从消息到记忆再到 Reflection 的端到端演示。关键边界没有未解决失败，Luke 能连续使用并给出具体体验反馈。进行一次合成故障定位和恢复，验证测试环境操作不能伤及用户库。时延按段汇总，包括上下文组装、召回、首段可见输出、工具、后台和总完成时间，每次报告带运行次数、Provider、模型、上下文规模和网络条件。流式显示只说明首段可见时间，不能当作总等待降低。数天日用提供体验信号，不能宣称长期可靠性已经证明。对未通过的年底目标明确记录，并与 Luke 决定后续。

### 学习活动与理解证据

Luke 在必要提示下解释完整链路，面对新错误判断先查哪层，并提出可验证的原因。间隔重访阶段 1 和阶段 3 的机制，确认能够迁移应用。学习笔记存放在既定私人目录，工程决定和验收证据仍在本仓库。

### 待确认问题

什么限制仍阻碍下一周继续使用。哪些机制能解释却还不能独立判断。后续优先做用户控制、日记还是语音，是否已具备邀请其他真实用户的条件。

## 后续阶段保留长期愿景

后续阶段不承诺日期，启动前重新调研和估算。以下顺序是推荐依赖，完整多用户不是最后才考虑的数据补丁。

| 阶段 | 目标与 feature & spec | 验收标准 | 学习重点 | 待确认问题 |
| --- | --- | --- | --- | --- |
| 6. 用户控制与可携带记录 | 完整纠正、遗忘、导出和删除，覆盖原始内容、记忆、画像与派生产物。 | 能追踪影响范围，重建不复活被遗忘内容；备份与供应商处理的限制明确；导出可读可用。 | 数据生命周期、依赖追踪、版本与恢复。 | 编辑与自然语言纠正如何分工，遗忘与审计如何兼顾。 |
| 7. 连续生活日记 | 从对话形成第三人称观察日记，支持回看，保留来源和推断边界。 | 不编造经历，不把推断写成事实；纠正与遗忘能传播到日记；真实使用者认可叙述方式。 | 派生视图、生成内容质量、变更传播。 | 日记粒度、语气、生成时机和编辑权。 |
| 8. Open Loop 与适时跟进 | 识别未完事项、变化和适合再问的时机，先明确跟进边界。 | 过时或已完成事项不再追问；用户可关闭，不施压或制造依赖。 | 事件与状态、时间调度、打扰成本。 | 只在对话内跟进还是允许对话外消息，通知渠道与静默时间。 |
| 9. 语音优先体验 | 根据文本闭环接入语音输入输出，再评估实时轮转、打断与恢复。 | 噪声、口误、中断与取消可处理，延迟和转写误差有实测，记忆不把识别错误当确定表达。 | 实时流、并发、回合边界与可恢复性。 | 原音频是否保存，文字与音频的权威关系，可接受等待和成本。 |
| 10. 完整多用户与长期运营 | 账户、邀请、租户隔离、恢复、费用与运维；对外前补齐产品和数据承诺。 | 多真实用户使用中隔离、删除和恢复可验证，配额和故障有可执行处理。 | 认证授权、运行保障、隐私与产品运营。 | 目标人群、年龄、危机处理、服务地区、商业边界与上线范围。 |

阶段 10 可与后续功能并行，前提是来源、隔离与清理基础已通过。邀请真实外部用户前必须先满足对应访问、隐私和产品承诺条件，不必等待语音或全部日记完成。

## 学习覆盖与预算复核

年底的学习目标仍是掌握 Harness 绝大部分重要且基础的知识。下面是覆盖核对，不是课程表或答题清单。是否形成理解，持续以当前代码和新场景中的实际判断为依据。

| 基础知识范围 | 主要所在阶段 | 可观察的理解依据 |
| --- | --- | --- |
| 执行生命周期、流式、取消、停止与有界循环 | 1 与 2 | 沿真实请求说明开始、执行、结束与部分失败的状态。 |
| canonical 数据、持久化、上下文窗口与预算 | 1 至 3 | 解释原始表达、派生内容和本次输入的关系。 |
| 工具协议、参数验证、权限与不可信输入 | 2，后续阶段重访 | 判断模型提议与应用执行的边界，定位失败。 |
| Provider 协议、能力差异与替换 | 0 至 2，5 回归 | 解释统一接口没有消除哪些差异。 |
| 记忆写入、检索、时间变化与依据 | 3 与 4 | 区分取不到、取错、推断错和回答错。 |
| 后台状态、重试、幂等与恢复 | 4 与 5 | 解释重复运行和中断对有效产物的影响。 |
| 行为测试、场景评测、观测、时延和成本 | 各阶段持续，5 整合 | 判断每种证据能证明什么，以及限制在哪里。 |
| 线上部署、配置、归属、访问与清理 | 0、1、5 | 说明数据与密钥去向，验证环境和用户边界。 |

复杂图编排、多 Agent 协作、任意代码沙箱、实时语音、训练与微调不是本轮基础机制的必要实现。阶段 0 复核这份覆盖是否符合 Luke 对原目标的期待，不能用完成一条演示链路替代广度要求。阶段 5 若仍有基础知识缺口，明确记录并安排后续，不宣布已全面掌握。

100 小时是低置信度的 Luke 参与预算，不是总工程工时。阶段 0 的 7 小时可粗分为路线比较 3 小时、Provider 与数据边界 2 小时、范围与 SPEC 讨论 2 小时。阶段 1 的 25 小时可粗分为真实链路与 UI 体验 10 小时、数据与失败边界 8 小时、运行讲解和复访 7 小时。其余阶段在启动时用体验、决策与讲解三类活动核算，不提前制造精确工期。

本轮计划讨论、阅读和审阅消耗计入阶段 0，不额外增加年底总额度。阶段 0 结束后按已用时间、Portal 适配和理解节奏重估全部预算。后台 Agent 的实现、验证和资料调查另记，不暗示它们无需工程时间。若阶段 0 剩余额度不足，先使用缓冲并说明用途，再决定是否调整后续。

## 学习节奏与延误处理

每阶段以一个完整机制示范开始，再沿真实代码和运行讲解，由 Luke 解释因果、做一次有意义的小判断或修改。Luke 也可以先说自己的判断，再看实际运行核对。隔几天在新场景重访，或在当前任务里用同一机制解决新问题。主 Agent 整理笔记并记录尚需引导的地方。对已经能解释的内容减少讲解，对混淆处回到实际输入和状态，不增加背诵、闭卷答题、考试或计时。记录学习理解的目的在于决定下次给多少引导，不给掌握程度打分，也不以是否“一次说对”判定通过。

每周可参考分配为体验与讨论 3 小时、代码和运行讲解 3 小时、阅读与关键判断 2 小时、记录与回顾 1 小时、机动 1 小时。这是弹性安排，碎片时间可拆分，学习不会作为实现之后的额外负担。

若预算吃紧，按顺序降级。先减少外部平台集成、装饰性 UI、非必要工具和自动化频率，再缩小记忆输入范围与比较候选数，然后缩减运行详情的覆盖维度，最后才推迟后台复杂度。若单周投入下降到约 5 小时，优先保住阶段 1 的部署对话、阶段 2 的人格体验和阶段 3 的基础跨日记忆。保留一次完整的工具循环、第二 Provider 的有限替换验证和有依据的 Reflection 闭环。不削减数据隔离、基本访问控制、来源区分、失败可见与基本清理。如果仍超出预算，带着实际完成情况和明确代价与 Luke 调整目标或日期，不静默取消 Reflection 或任何既定目标。
