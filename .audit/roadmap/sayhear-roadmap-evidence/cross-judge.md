## 二、推荐基底：候选 1

候选 1 是唯一同时满足六项且没有单列问题的候选，选作可继续维护的基底。理由：

1. **范围零漂移。** 年底目标、`fact`/`opinion`/`profile` 不预设为表、日记与完整纠正遗忘后移、Open Loop 与语音出年范围，全部与 CONTEXT 逐条对齐，没有任何一处把后续范围提前拉进年内，也没有静默降级条款。
2. **选型保持开放而收敛。** AI SDK 是"推荐默认候选"而非既定决定，Mastra 保留为强替代并给出对称的判据（省下的适配量 vs. 必须绕过其 memory/存储的代价），LangGraph 与 Claude Agent SDK 给出与产品质量无关的拒绝理由。数据库只给"优先讨论候选"并明确"不依据未核实的免费额度或价格"，符合 CONTEXT "新增复杂度应有实际需求和明确理由"。
3. **验收锚定真实行为。** 每个阶段都有用户能感知的结果、阶段结束所需证据、学习证据、待确认项四件套，并配退出条件（第 3 周冻结平台扩展、第 7 周缩小记忆写入、第 9 周只收敛）。这是四份中唯一把"砍什么、何时砍、砍到什么程度"写成可执行规则的。
4. **证据纪律。** Tolan 正文 403 只用搜索摘要并标注为供应商自述；旧 companion 研究对 Pi 记忆编辑的描述冲突被显式记录；来源按"能力文档 / 产品说明 / 供应商案例 / 学习研究"分级并说明各自不能证明什么；明确不采用旧资料中的延迟、留存与 benchmark 数字。
5. **学习预算结构最可信。** 每周 3+3+2+1+1 含 1 小时机动，理解证据按"需引导解释 / 可独立解释 / 能在新场景应用"持续记录而非一次盖章，明确不以提交数和笔记字数判断进度。

候选 1 的已知弱点（不改变选型结论）：全文 234 行、密度高，读者负担明显重于其他候选；100 小时全额分配，只靠 12-29 至 12-31 三天日历缓冲，没有预留小时级缓冲；未固定任何包版本号，实施时需重新核对。这三点在第四节对应标准 2 与标准 5 的扣分。

## 三、可提取的改进（每份未选候选最多两项）

### 来自候选 3

1. **旧项目记忆失败的四分类，作为记忆阶段验收场景的生成器。** 候选 3 把旧项目的连续记忆失败拆成：不知道自己只看到部分历史、该联想时没发起查询、查了但词法不匹配、找到旧状态却漏了最新状态，并指出只有第三类由检索技术决定。这套分类比候选 1 现有的"同名人物、转述他人、偏好变化、否定、时间相对表达"清单多出一维：它要求验收同时覆盖"模型是否知道自己看的是局部"和"新证据是否压过旧证据"。建议并入阶段 3 的验收场景集，与候选 1 已有的 20 个场景并集使用，不替换。
2. **来源分级标注与"弱点自陈"两件写作惯例。** 候选 3 对每条来源标 `[本次核实] / [旧研究] / [二手]`，并在文末单列"本候选的弱点"六条。这是低成本的可审计性改进，建议基底在定稿时采用，使后续主 Agent 综合时能直接看出哪些结论可以升格为决定、哪些必须留在待实测。

不采用候选 3 的"先预测、后解释"学习协议作为提取项：它是有价值的做法，但候选 1 已有等效的"沿真实运行解释因果 + 隔几天在新场景重新讨论"，重复提取收益低。

### 来自候选 2

1. **记忆组件的四问验收门。** "它记住的内容来自哪里、表达者是谁、什么时候成立、当前回复为什么选中它。"这四问比候选 1 现有的"来源映射、时间变化、中文、删除行为"更贴近产品语义，且可直接作为阶段 4 唯一外部候选（Mem0）的通过/停止判据。建议替换候选 1 阶段 4 中较笼统的"通过来源、时间变化与隔离检查"表述。
2. **时延按段记录并要求分母。** 首段可见、总完成、检索、工具、后台分开记，并报告样本量、网络与 Provider 条件，明确"不把流式显示当作总时延降低"。候选 1 的验收里没有时延维度，这是实质缺口；Provider 能力差异（CONTEXT 明确要求"明确处理"）目前缺少可观察的验收口径。

### 来自候选 4

1. **15 小时不预分配缓冲。** 候选 4 计划目标 85 小时、显式留 15 小时不预分配，并规定未用完时"留作年底验收和连续记忆缺陷修复，不新增范围"。这直接修补候选 1 的预算可信度问题：100 小时全额分配对一个入门独立开发者过于乐观，建议基底改为计划约 85-90 小时、显式留 10-15 小时缓冲。
2. **投入下降时的降级阶梯。** "保住阶段 1 部署对话、阶段 3 人格体验、阶段 4 基础跨日记忆；先推迟 Reflection，再缩减运行详情，最后才增加后台复杂度；若基础聊天失败体验和数据隔离未过关，取消年内 Reflection 范围。"候选 1 已有停止条件但缺少按优先级排序的降级顺序，此项可与其现有停止条件合并为一张表。

## 四、逐项评分依据与扣分点

### 标准 1：与 CONTEXT 一致

- 候选 1（5）：六项年底目标全部在位；"完整纠正与遗忘"只要求基础查看与清理，明确写出"完整自然语言纠错、联动遗忘及日记重建留后续"；把"日记、对话外主动消息、浪漫角色系统"显式排除。
- 候选 2（5）：同样范围对齐，"基础内容查看与清理不能后置"表述清楚，并正确指出"若基础清理无法可信完成，就不开放长期真实数据使用"。
- 候选 3（4）：愿景对齐，但 **P2 把"纠正后下一轮不再召回旧内容"和"遗忘后原文、观察、画像、缓存路径都不得再出现"写进年内 30 小时**。CONTEXT 将完整纠正与遗忘列为后续推进，年内底线是基本查看与清理。把跨四层的传播链路纳入年内是范围前置，且它自己承认"如果 3 周内无法同时做到来源可展开与删除不复活，缩小范围……把画像留到 2027"——说明作者知道做不完。这不属于"擅改年底目标"（它没有缩小目标），但属于把后续范围提前拉入，增加主线风险，单列记录。
- 候选 4（4）：范围总体对齐，但两处与 CONTEXT 冲突。其一，阶段 2 写"明确工具是否属于年内必需范围"，而 CONTEXT 年底目标明确包含"工具调用"，这不是开放问题而是既定需求，列为需求遗漏。其二，结尾写"若基础聊天的失败体验和数据隔离没有过关，取消年内 Reflection 范围"——CONTEXT 规定"范围或时间需要调整时，与 Luke 明确讨论"，静默取消属于流程违规，单列记录。

### 标准 2：调研覆盖与证据

- 候选 1（4）：覆盖 6 个 Harness、4 个记忆方案、2 个数据库、3 个任务方案、2-3 个观测平台、4 个产品参照、2 项学习研究，分级说明每类来源能证明什么。扣分：未固定任何版本号；缺 Hindsight、Honcho 等较新记忆候选；Tolan 与旧 companion 研究的多处冲突只做了记录而未尝试第三方核验。
- 候选 2（4）：分层表完整，25 条来源逐条附限制说明，主动记录 Mem0 图记忆文档三处互相矛盾（搜索摘要、官方页、GitHub README）并拒绝沿用旧结论。扣分：无版本快照；未核实任何套餐价格（自己声明"不在路线里引用猜测价格"，处理正确但覆盖因此偏薄）。
- 候选 3（4）：覆盖面最广、标注体系最细（本次核实/旧研究/二手 + npm 版本快照 + 弱点自陈）。扣分且问题最重：**大量价格与配额数字未复核**——Zep Flex $125/50,000 credits、Honcho $2/百万 token、Rosebud $12.99/月、Neon 免费 1 GB/100 CU-hours/10 分支、Supabase 免费 500 MB/一周暂停、Vercel Hobby 300 秒/Pro 800 秒、Workflow 50,000 events 每月等；以及"Zep 社区版退役"仅来自一个二手 GitHub 仓库。这些都不能当共识。另外，用"Mastra Observational Memory 的 resource scope 已 deprecated""Semantic Recall 默认关闭会增加时延"作为拒绝整个框架的主要理由，本次无法核实，应降级为待核实而非拒绝依据。
- 候选 4（3）：分层层级清楚，每项都附官方链接与限制，引用 LongMemEval 与 MemoryAgentBench 作评测维度来源是好的。扣分：完全没有版本或套餐核实；把 OpenClaw 列为"直接迁移"的替代方案并以其安全页作论据，但这是个人助理形态，与消费级多用户 Web 的产品目标不同层，作为备选基线缺乏论证；Replika 与 OpenAI Memory FAQ 两条标为旧研究且 Replika 本次抓取 403，却在产品参照表中正常使用。

### 标准 3：可理解、可替换、可维护，不提前引入复杂度

- 候选 1（5）：平台分层表 + "同层只保留一个主实现" + "每个新增服务都需说明它替代了哪些工作、引入哪些状态与运维责任"，并明确对约 100 小时学习预算取舍。不把"全部历史永远塞入模型"当产品策略，也不为自建找保留理由。数据库选择明确说"先核验区域、连接池、扩展、备份与恢复及当前套餐，然后决定"。
- 候选 2（4）：职责划分清晰（"数据库不是记忆策略，向量索引不是用户画像，trace 不是 canonical 历史，checkpoint 不是长期生活记录"），一条主 Harness、一个数据库服务、一个追踪平台。扣分：把 Vercel Workflow 纳入候选但未分析其 payload 保留对私人内容的含义；未给每个阶段写退出条件。
- 候选 3（3）：**提前固定整套栈**。P0 即锁定 AI SDK 7 原语、自有上下文组装、Neon、两个独立 Neon 项目、原生 SQL；P1 即锁定 FTS+pgvector 混合检索、`search_past` 工具、覆盖范围说明；后台即锁定 Vercel Workflows 且 payload 只放 ID；记忆挑战者直接点名 Hindsight。CONTEXT 明确"下一步共同制定搭建与学习计划，再选择 Harness、Memory、数据库和 Provider"，且"新增复杂度应有实际需求和明确理由"。候选 3 在 Luke 尚未共识前把五层选型全部定死，其中 Workflow 的 payload 保留策略还是它自己列为"待讨论"的隐私问题。可替换性设计（记忆端口三动作）是好的，但被早期锁定抵消。扣 2 分并单列。
- 候选 4（4）：分层比较 + "先证明一条路径有用，再扩大记忆能力" + 显式拒绝多记忆系统并行，方向正确。扣分：核心运行时选择留空（"是否选一项主要 TypeScript agent/工作流方案做小型替代性验证"列为待讨论），使阶段 1-2 的搭建计划缺少可执行主线；对一个需要"可继续维护"的基底，这是实质缺口。

### 标准 4：阶段依赖与可观察验收

- 候选 1（5）：每阶段四件套（用户可感知结果 / 阶段结束证据 / 学习证据 / 待确认项），验收全部可观察：刷新后历史仍在、流中断不伪装完整成功、工具循环有结束预算、重复请求不产生混乱历史、测试凭证不能操作用户库、两个合成用户验证不串读。停止条件带周次。人格验收落到具体场景（抱怨工作时先理解、有害自我评价时保持判断、用户叫停时停止追问、隔日提起时允许用户已改变）。
- 候选 2（4）：验收可观察（合成会话刷新后可继续、错误不伪装完整、测试凭据不能访问用户库、来源能回到真实记录、停用后不再注入、重复运行无重复生效）。扣分：无逐阶段退出条件，只有第 4/6/8 周的检查点；阶段 5"约一半时间用于部署与日常体验复核，另一半作为返工与学习缓冲"过于含糊；五个阶段各 20 小时刚性均分，没有为记忆与 Reflection 的不确定性留余地。
- 候选 3（4）：验收最具体可测：10 轮无重复无丢失、停止后数据库无追加、主动制造 Provider 超时、运行详情消息序列与数据库一致、删除后三条路径都不返回、后台重试观察数量不增加、时延带分母。扣分：**阶段负载不均**。P1 三周内要做上下文契约 + 混合检索 + 覆盖范围 + 时延记录；P2 三周内要做观察 + 画像 + 纠正 + 遗忘传播 + 幂等后台。作者自陈弱点第一条即"自建 loop 的时间估计可能过于乐观"，P2 的负载与之叠加，依赖顺序存在实际风险。
- 候选 4（3）：阶段 0 要求"候选项各自有可证伪理由"是好的，阶段 5"同一批输入重跑结果可比较"可观察。扣分：阶段 2 把工具调用留待决定（需求遗漏，见标准 1）；阶段 6 仅 7 小时却要承担端到端演示、失效/清除测试、线上冒烟、回归案例与阶段文档，明显过薄且依赖 15 小时缓冲兜底；全文没有一条带周次的停止条件，落后时只有一条"取消年内 Reflection"的硬切换。

### 标准 5：学习融入与 10 小时预算可信

- 候选 1（5）：每周 3 小时体验与讨论、3 小时沿代码讲解、2 小时阅读判断、1 小时回顾笔记、1 小时机动；每阶段一次完整机制示范 + Luke 沿真实运行解释 + 一个小变化判断 + 隔几天新场景重讨论；理解证据三态持续记录；引用 Dunlosky 综述并说明"不能直接推导独立开发者十周掌握大部分 Harness 知识"。学习时间明确排在正常使用反馈之内，"不把学习放成开发完成后的额外任务"。
- 候选 2（4）：每周 4+2+2+1+1，每阶段学习证据具体（沿请求说明职责、指出失败属于哪层、区分"没取到/取错/取到了但说错"）。扣分：100 小时全额分配、无缓冲；引用 Chi 1989 自我解释研究但未给适用边界；学习方法一节短于其他候选，缺少对" Agent 代劳导致理解空心化"的防护。
- 候选 3（4）：每周 2+3+3+2，方法表列出效应量与边界（Bisra g≈0.55、Kobayashi 准备教 g≈0.35/准备加教 g≈0.56 并明确"不能当作掌握的证据"）， anti-metacognitive-laziness 协议有 Bastani 2025 与 Fan 2024 两项依据，每阶段四件学习产物。这是四份中学习设计最细的。扣分：**100 小时全额分配、仅 0.3 周（约 3 小时）缓冲**，与其自陈"100 小时能否覆盖本文范围是最大的未知"矛盾；Bastani 的 48%/17% 是经 Wharton 解读的二手转述，作者已标注，但仍在协议中被当作主要论据。
- 候选 4（4）：85 小时计划 + 15 小时显式不预分配，并规定未用完时的用途，是四份中预算结构最诚实的；投入下降时的保序与降级顺序具体。扣分：没有每周时间分配，只有阶段级小时；学习循环（闭卷讲调用路径 + 做一个小改动）描述正确但比候选 1 和 3 单薄；没有对" Agent 代劳"的防护条款。

### 标准 6：四类状态区分

- 候选 1（5）：开篇即分"已定 / 推荐 / 待讨论 / 待实测"四节，且每节内容与后文一致；研究推荐明确写成"这是项目适配判断，不能从官方能力文档推导出某框架产品效果更好"；待实测列出五项具体不可推断项（Provider 兼容协议、框架是否交得出完整运行输入、中文跨日记忆是否有用、Reflection 是否引入固化标签）。
- 候选 2（4）：有四态表，且"待实测"六项具体。扣分：开篇两大段推荐（AI SDK 支撑、Mastra 比较）写在四态表之前，读者容易先记住结论再看状态；文中"推荐"与"待讨论"的边界偶有混用（如数据库推荐写"先在 Neon 与 Supabase 二选一"，随后又说选型权重资料不足，实际是待讨论）。
- 候选 3（5）：第 7 节把已定/推荐/待讨论/待实测分成四张清单，每条一句话，且与正文主张严格对应；来源三级标注；第 10 节自陈弱点。区分度四份中最清晰。
- 候选 4（4）：有已定/推荐/待讨论/待实测四节，且"待实测"明确写"不实测就不能写进结论"。扣分：部分推荐缺少状态标注（如"自有 PostgreSQL + 可选 pgvector"在分层表中直接写"推荐持有原始会话"，未说明这是研究推荐而非决定）；"重要取舍"六条混合了已定共识与本候选判断，未标注。

## 六、资料事实与研究推荐的边界

- **资料事实（四份候选可互相印证的公开文档能力）**：AI SDK 提供循环控制与 Provider 抽象且不同 Provider 能力有差异；Mastra 的 Memory 需要 storage provider；LangGraph 生产持久化需要 checkpointer；Claude Agent SDK 运行 Claude Code binary 且是自营进程；Vercel Cron 失败不自动重试、可能重复或漏发；Inngest/Trigger.dev 的幂等键不等于外部副作用恰好一次；Vercel 不再自营 Postgres 而由 Marketplace 接入。这些只支撑"提供何种机制"。
- **候选自报、本次未复核**：一切版本号、价格、免费额度、函数时长上限、Workflow 事件配额、竞品月费、LoCoMo 或厂商 benchmark 数字、竞品留存与召回提升数字。不得写入任何决定。
- **研究推荐（非 Luke 已接受）**：AI SDK 作为默认 Harness、Supabase/Neon 的优先讨论顺序、Mem0 作为唯一外部记忆验证候选、Inngest/Trigger.dev 在自动化后才引入、Langfuse 或最小本地实验记录、十周四/五/六阶段的切分。这些是本评审与各候选的判断，需在阶段 0 与 Luke 共识后才成为决定，并落入 ADR。
- **待用户决定**：首个 Provider 与数据区域、预算上限、可接受等待、初期访问对象是否仅 Luke、embedding 供应商与私人文本外发边界、运行详情默认可见程度、记忆范围与"令人感到被监视"的召回。
- **待实测**：Provider 兼容协议对流式工具调用/取消/结构化输出的覆盖、框架能否交出完整运行输入、中文跨日对话中记忆是否有用、Reflection 是否引入固化标签、混合检索能否修复换措辞漏召回、回合内召回能否把时延压到可接受、外部记忆候选扣除新服务成本后是否有净收益。
