# Learning stage

推进产品目标与 Luke 的理解。遵循 `AGENTS.md`、`CONTEXT.md` 和阶段共识；围绕真实产品学习，理解成熟实践的适用条件与取舍，不刻意试错。

## 启动与接续

1. 查 `git status`，保留并行改动。读入口、共识、阶段计划、Issue 或 working spec 及明确链接；经 `docs/decisions.md` 检索相关 ADR，按需读 Glossary。未变材料不重读，不扫描全历史。
2. 新阶段或新功能从最新 `origin/main` 建立工作分支；恢复会话沿用原分支，不重置或混入并行改动。找 `docs/plans/stages/stage-N/features/<feature>/session.md` 或既有接续记录；核对来源、时效与冲突。区分授权、决定、推荐、待验证、完成，文件日期和名称不代表共识。
3. 主动提出本次目标与议程，涵盖体验目标、学习机制、调研问题、决策点、完成条件、步骤及理由。目标明确直接安排；不明时先推荐，只问影响方向的问题。阶段范围、关键架构和产品边界变更由 Luke 确认。
4. 按 [records.md](references/records.md) 创建或更新接续记录；启动、决定、环节切换、知识点结束与收尾均及时落盘。

## 选择下一环节

主 Agent 拆目标、综合证据、推荐、讨论、讲解并维护记录。允许往返，跳过已满足环节；切换时说明当前问题与理由，议程不等于决定。

- 事实或机制不明：定点调研，得到可追溯证据或明确未知及影响。
- 决策点不清或目标、取舍、理解有分歧：按需调用 `grill-with-docs`，明确问题、分歧与决策人，推进共识。
- 证据足够：推荐并确认重要选择，记录接受或推迟、依据和适用条件。
- 缺少决策所需理解：先讲解或演示，依实际回应补充；其余知识记录回访，允许已确认范围的后台调研继续。
- 目标、关键决定与验收明确：读 [spec-handoff.md](references/spec-handoff.md)，复用 `to-spec` 产出详细 SPEC，再按当前 Git/GitHub 授权整理阶段文档、commit、调用 `pr` 发 PR 并确认合入 main，才完成交接。提前讨论验收与测试边界；后续构建和新阶段从最新 main 开始。

## 调研与委派

按需复用 `poteto-mode` 及相关 principle；`how` 查机制，`why` 查依据，`research` 查外部事实，不载入无关构建流程。技能按运行时目录解析并读入口、平台映射；pstack 从已安装 `poteto-mode` 解析同级技能，不固定缓存版本。缺失时说明并继续独立工作，不伪称调用。教学与 SPEC 技能复用已获授权，外部操作仍按当前授权。

调研先定问题、影响的决定、证据要求与停止条件。通常比较成熟主选和最强替代，足以决策即停；仅为会改变选择的重要未知扩展调查。优先当前官方资料、固定版本源码、实际观测，区分文档能力、推断、实测并保留置信度。采用前重核易变事实，旧仓库结论不直接成为 v2 共识。资料无法回答且影响决定时，设计有限验证及停止条件，交相应工作流执行。

采用 chief-of-staff 的协调与文件指针方式。委派独立批量阅读、专项调查、反方检查，主会话保持对话；小而紧耦合的查阅自行完成。依仓库规则优先 `delegate-claude`，记录真实失败后才 fallback。

任务书含目标、授权边界、文件指针、证据要求、独立输出位置和完成条件。worker 不共写阶段状态、SPEC、学习索引；只返回摘要、证据指针、未知与限制。主 Agent 查结果及 warnings，核实影响决定的证据，不以 completed 代替验证。

## 讨论与决策

默认中文 ELI5，调用 `pstack:unslop` 覆盖议程、比较、提问、讲解。先用最小完整解释讲清问题、机制、结果，再随回应展开；一次一个概念，用产品实例或小图。术语首次解释后统一名称；类比按需并说明局限。简洁但保留决策条件、风险、证据，不幼儿化。

需深入梳理决策点或检验取舍时调用 `grill-with-docs`，复用其 `grilling` 与 `domain-modeling`，边讨论边维护 ADR 和已澄清术语。重要选择说明问题、约束、证据、选项、推荐、代价及重评条件。先补齐必要理解再请 Luke 选择；事实由 Agent 查，偏好与产品取舍由 Luke 定，重要架构与范围在实现前达成共识。可逆常规整理、调研自行推进。

所有构建、开发、产品体验决策点均建立或关联 ADR，用 `domain-modeling` 格式并更新索引，覆盖其“仅重要且难逆取舍”的筛选规则。相关点可合并但须逐项可追溯。未定为 Proposed 或草稿，列选项及待确认项；共识后及时记录状态、决定、依据、取舍、重评条件。接续记录与 SPEC 链接 ADR。ADR 与学习计划、笔记并行，互不替代。区分推荐、反方、暂缓、拒绝；未实测不写通过。

## 学习

复用 `pstack:teach` 的机制与原因讲解、`teach` 的目标、资源和长期理解记录；按问题范围调用 `how`、`why`。每个知识点围绕当前阶段，明确学后能解释或判断什么、已有理解、演示或问题。结合代码、真实运行或标注示例，区分拟议与已运行行为，不以函数清单代替机制。

自然反问真实场景的失败归属或方案取舍，不背诵、不考试、不反复打断。依回应补讲，后续相关讨论回访。答对一次仅是当次证据，无回应记未确认，讲过或写完笔记不等于掌握。

每个完整知识点结束按 [records.md](references/records.md) 同步 Markdown 主题笔记与独立学习记录，阶段末整理索引。HTML 按需，不默认建立整套课程。收尾记录 SPEC 位置、待验证项、理解回访点与构建第一步；SPEC 完成不代表实现或验收完成；阶段交付还须完成文档归类及 PR 合入，细则见 SPEC 交接指南。
