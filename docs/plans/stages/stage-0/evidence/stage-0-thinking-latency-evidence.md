# 阶段 0：限制模型思考时间的手段与实际时延

执行日期：2026-10-22。范围仅两条路线：OpenCode Go（`deepseek-v4.1-flash`）与 DeepSeek 官方 API（`deepseek-flash`）。Luke 已授权本次从本地 `.env` 读取 `OPENCODE_API_KEY` 与 `DEEPSEEK_API_KEY`，仅用于本验证。脚本只读取这两个变量，不执行 `.env`，不打印、不回显、不写入任何密钥；产物与日志中无密钥、无请求头。提示词为自拟合成内容，不含任何私人数据；未连接数据库、未部署、未创建资源。

本次共发出 **15 次真实请求**（12 次矩阵 + 2 次 `max_tokens` 边界观察 + 1 次 usage 形状补测），全部返回 HTTP 200，无重试，单次 90 秒截止。所有请求均为流式（`stream: true`，`stream_options.include_usage: true`），`max_tokens: 2048`（边界观察除外）。每组组合只跑 1 次，**样本不具统计意义**，只能说明“这条路上能发生什么”，不能给出分布、P50/P95 或性能基线。

## 1. 文档层

### 1.1 DeepSeek 官方 API

来源：官方 [Thinking Mode 指南](https://api-docs.deepseek.com/guides/thinking_mode) 与 [Create Chat Completion 参数页](https://api-docs.deepseek.com/api/create-chat-completion)，2026-10-22 重读。

| 问题 | 结论 | 原文 / 等级 |
| --- | --- | --- |
| 能否关闭思考 | 能。Chat Completions 用 `thinking.type = "disabled"`；参数页另有 `reasoning_effort: "none"` 关闭思考 | 参数页：`thinking` “Controls the switch between thinking and non-thinking mode.”，`type` 取 `enabled`/`disabled`，默认 `enabled`；`reasoning_effort` “`none` disables thinking mode; `low` / `high` / `max` enable thinking mode.” `[文档]` |
| `reasoning_effort` 可选值 | 参数页枚举为 `none`、`low`、`high`、`max`；指南页（OpenAI 格式）只写 `low/high/max`，并给出映射表 | 指南：“`{"reasoning_effort": "low/high/max"}`”；“minimal → low, low → low, medium → high, high → high, xhigh → high, max → max, ultra → max” `[文档]` |
| 默认 effort | `high` | “Thinking mode is enabled by default, with the default effort being `high`” `[文档]` |
| 思考 token 预算/上限参数 | 没有独立的数值型“思考预算”参数。唯一影响思考量的是 `reasoning_effort`；`max` 同时把默认 `max_tokens` 抬到 128K | 参数页只把 `reasoning_effort` 描述为 “Controls the thinking mode toggle and the thinking effort.”；未出现 thinking budget / max thinking tokens 字段 `[文档]` |
| `max_tokens` 是否约束思考 token | 文档**没有明说**“包含思考 token”。但文档给出了思考模式下的默认上限，且 usage 把思考 token 单列 | “The maximum number of tokens that can be generated in the chat completion.”；“When not set, the default is 8K in non-thinking mode, 64K in thinking mode (128K with `reasoning_effort` set to `max`).”；usage 字段 `completion_tokens_details.reasoning_tokens` “Tokens generated by the model for reasoning.” `[文档]`；是否包含由第 2 节实测回答 |
| 思考模式下不支持的参数 | `temperature`、`presence_penalty`、`frequency_penalty` 不生效且不报错 | “Thinking mode does not support the `temperature`, `presence_penalty`, or `frequency_penalty` parameters.”；“setting these parameters will not trigger an error but will also have no effect.” `[文档]` |
| 思考内容流式位置 | `delta.reasoning_content`，与 `content` 同级 | “In thinking mode, the chain-of-thought content is returned via the `reasoning_content` parameter, at the same level as `content`.” `[文档]` |

### 1.2 OpenCode Go

来源：[OpenCode Go 页面](https://opencode.ai/docs/go/)，2026-10-22 重读。页面章节为 How it works / Where can I use it / Usage limits / Endpoints / Privacy / Background / Goals。

| 问题 | 结论 | 原文 / 等级 |
| --- | --- | --- |
| 能否关闭思考 | **文档未写**。Go 页面通篇没有 reasoning / thinking / effort / max_tokens 任何一节 | 页面只规定客户端行为：“Send typical coding agent traffic”“Identify itself with its own user agent”“Send a stable session ID in `x-opencode-session`” `[文档]` |
| `reasoning_effort` 可选值 | **文档未写**，因此也没有“Go 不支持某项”的可引原文 | Go 页面无相关字段；`[文档]` 为空白，不是“不支持”的证据 |
| 思考 token 预算/上限 | **文档未写** | Go 页面只列按上下文分档的计价阈值（如 “Grok 4.7: ≤ 200K tokens / > 200K tokens”），不涉及思考预算 `[文档]` |
| `max_tokens` 是否约束思考 token | **文档未写** | Go 页面无 `max_tokens` 说明 `[文档]` |
| 模型与 endpoint | 模型 ID `deepseek-v4.1-flash`；OpenAI 兼容路径 `https://opencode.ai/inference/go/openai/v1/chat/completions` | 页面 Endpoints 节列出该 URL 与模型 ID `[文档]` |

补充：OpenCode 的 [Models 页面](https://opencode.ai/docs/models/) 讲的是**客户端配置**（`provider.<id>.models[...].options` 下的 `reasoningEffort`、Anthropic 的 `thinking.budgetTokens`）与 variant，不是 Go 推理接口的参数契约。不能把客户端配置的字段名当作 Go endpoint 已文档化的字段。`[文档]`

**文档层结论**：官方 API 对“关闭思考、effort 取值、默认 effort、思考模式不支持的参数”都有明确契约；Go 对这些**全部未文档化**。因此 Go 侧的参数行为只能靠实测，且实测结论不能反过来当作稳定性承诺。

## 2. 实测层

### 2.1 方法

- 脚本：`/Users/lukemyself/.claude/jobs/470196ef/tmp/thinking-latency-probe.mjs`；脱敏结果：同目录 `thinking-latency-results.json`；补测 usage 形状：`usage-probe.mjs`。临时目录会随 job 删除。
- 两条路线 × 3 种设置 × 2 个提示，各 1 次：
  - `disabled`：`thinking: {type: "disabled"}`
  - `low`：`thinking: {type: "enabled"}` + `reasoning_effort: "low"`
  - `high`：`thinking: {type: "enabled"}` + `reasoning_effort: "high"`
- 提示词（合成）：
  - `simple`：“你好，今天天气不错。用一句话回应我。”
  - `medium`：小卖部 A/B 两种商品的二元一次方程组应用题（A 成本 12 售 20，B 成本 7 售 11，共卖 40 件、销售额 665 元，求各多少件）。正确答案 A=25、B=15，需要列式并解方程。
- 计时口径：`t0` 为 fetch 发出前；首个 reasoning 片段与首个可见正文片段（TTFV）都按收到该 SSE chunk 的时刻计。`completedMs` 为收到 `[DONE]` 或流结束的时刻。均含网络往返与排队，不是纯模型算力时间。
- 单次截止 90 秒，无重试（等价 `maxRetries: 0`）。401/402/余额类错误会立即停该路线；本次未触发。

观察：

- **参数被接受**：12 次全部 200、正常 `stop`、`[DONE]`，没有任何 400/422。两条路线都接受 `thinking` 与 `reasoning_effort`，没有“被拒绝”的迹象。`[实测]`
- **思考开关确实生效**：`disabled` 下两条路线都没有任何 `delta.reasoning_content`；`low`/`high` 下都有。Go 的 usage 在 disabled 下明确报 `reasoning_tokens: 0`。`[实测]`
- **官方 disabled 的 reasoning token 数不可得**：补测确认其 usage 只有 `prompt_tokens_details.cached_tokens`、`prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`，**完全没有** `completion_tokens_details`。因此该项记 unknown，不能推断为 0。`[实测]`
- **effort 是否真的改变思考量，本次无法确认**：Go 上 `low`→`high` 在 simple 提示下 reasoning token 反而从 67 降到 44，在 medium 下从 98 升到 132；官方在 simple 下 60→65、medium 下 163→187。方向不一致，单样本下与“请求被接受但 effort 影响很小/被忽略”都相容。`[实测]` 不足以判定 Go 支持 effort 语义。`[推断]`
- **时延**：两条路线的 TTFV 都落在 0.7–2.0 秒；思考模式只比 disabled 多 0.3–1.1 秒，主要因为本次提示短、reasoning 只有 44–187 token。完成时间 0.9–3.2 秒。`[实测]`
- **未观察到 disabled 导致答错或明显变短**：medium 在两条路线的三种设置下都出现了 A=25、B=15。相反，disabled 的可见正文更长（Go 839 字符 vs 341–380；官方 672 vs 343–372）。这只说明“这 1 次没退化”，**不作质量结论**。`[实测]`

### 2.3 边界观察：`max_tokens` 是否卡住思考 token

对 medium + `high` 把 `max_tokens` 降到 64，两条路线各 1 次：

| 路线 | HTTP | reasoning tokens | completion tokens | 首个正文 | finish_reason |
| --- | --- | --- | --- | --- | --- |
| Go | 200 | 64 | 64 | 无 | `length` |
| 官方 | 200 | 64 | 64 | 无 | `length` |

两条路线的 reasoning token 都正好顶到 64，`completion_tokens` 也正好 64，且没有任何可见正文。这说明 `max_tokens` 是**思考 + 正文共享的总生成预算**，思考会把预算吃光并让正文为空、结束原因为 `length`。`[实测]`

这与官方文档“未显式说明是否包含思考 token”并不矛盾：文档没写，实测给出了包含关系。`[文档]` + `[实测]`

**对产品的影响**：把 `max_tokens` 当作“回答长度上限”来设，在思考模式下会变成“思考+回答总上限”，过小会得到空回答而不是短回答。这是比时延更值得注意的坑。`[推断]`

## 3. 结论

1. **能否把 TTFV 压到几秒内：两条路线都可以，且不只靠关闭思考。** `[实测]` 本次所有 12 个组合的 TTFV 都在 0.7–2.0 秒。`disabled` 给出最低 TTFV（Go 1.0–1.1 秒，官方 0.7–0.9 秒）；`low`/`high` 也只到 1.3–2.0 秒。
2. **若目标是“首字尽快出现”，首选 `disabled`。** `[实测]` 它在两条路线上都省掉 reasoning 片段，且本次 medium 题没有答错。代价迹象：官方 disabled 不返回 reasoning token 明细，无法从 usage 侧核对思考成本；回答更长（本次 medium 正文多约 80%–100%），意味着总完成时间不一定更短（Go disabled medium 3.2 秒，反而比 `low` 的 2.3 秒慢）。`[实测]`
3. **若希望保留思考，`low` 是本次时延/思考量的折中点。** `[实测]` Go `low` medium：98 reasoning token、TTFV 1.6 秒、完成 2.3 秒；官方 `low` medium：163 token、TTFV 1.9 秒、完成 2.6 秒。`high` 在两条路线上都比 `low` 多 30%–50% reasoning token，TTFV 多 0.1–0.3 秒。样本 1 次，不能当作稳定排序。`[实测]`
4. **Go 的思考参数是“可用但未文档化”。** `[文档]` Go 页面没有任何 thinking/effort 契约；`[实测]` 本次 6 次带思考参数的 Go 请求都被接受并返回 `reasoning_content`。因此可以用于阶段 1 实验，但**不能当作 Go 的稳定承诺**：字段名、默认值、effort 语义都可能在无通知下变化。生产上若要依赖，应保留“发 disabled 不生效时仍能工作”的降级路径。`[推断]`
5. **`max_tokens` 会与思考共享预算。** `[实测]` 64 token 时两条路线都被思考吃光、正文为空、`finish_reason: length`。因此“限制思考时间”不能靠调小 `max_tokens` 实现，那只会把回答截断；能限制思考量的是 `disabled` 或 `reasoning_effort`。`[实测]` + `[推断]`
6. **没有找到独立的“思考 token 预算”参数。** `[文档]` 官方只有 `reasoning_effort` 档位；`max` 会抬高默认 `max_tokens` 到 128K，而不是设置一个思考上限。`[实测]` 也没有发现任何请求字段能让 reasoning token 精确封顶（除共享的 `max_tokens`）。若阶段 1 需要硬性思考上限，只能靠 `max_tokens` 总量或 `disabled`。`[推断]`

## 4. 未知项与限制

- **样本量**：每个组合 1 次，共 15 次请求。无重复、无交叉、无并发对照，不构成性能基线，也不能区分模型差异与网络抖动。
- **提示规模小**：输入 80–106 token，reasoning 44–187 token。真实 SayHear 多轮对话的上下文和思考量会更大，“几秒内”的结论**不能外推**到长上下文或复杂任务。
- **未测默认值**：没有发“不带任何 thinking 参数”的基线请求，因此“默认 effort = high”只有文档依据，未实测。
- **未测 `reasoning_effort: "none"`**：官方参数页列了 `none`，本次用 `thinking.type: disabled` 关闭，没有验证 `none` 单独使用是否等价，也没验证 Go 是否接受 `none`。
- **未测 `max`**：官方文档称 `max` 会把默认 `max_tokens` 抬到 128K，本次未发 `max` 请求，未验证时延与 token 量。
- **未测流式工具调用下的思考**：本次无 tools，因此没有覆盖“必须回传 `reasoning_content`”的路径，也没有测工具轮次的时延。
- **未测错误路径**：没有制造 401/402/429/额度用尽，不知道 Go 在额度耗尽时是否仍返回 200 或改变思考行为。
- **Go 的 effort 语义未证实**：见 2.2，方向不一致，无法确认是被接受并生效、被忽略，还是仅噪声。
- **计时口径**：TTFV 含 DNS/TLS/排队/网络，不等于模型首 token 算力时间；未分离冷启动与连接复用。每条请求都新建 fetch，Node 默认可能复用连接，未控制。
- **`completedMs` 语义**：为收到 `[DONE]` 或流结束的时刻，客户端随后主动 `reader.cancel()`；未验证上游是否已停止计费。
- **模型快照**：Go 返回 `deepseek-v4.1-flash`，官方返回 `deepseek-flash`；仍不能证明两者是同一权重快照（沿用 `stage-0-provider-evidence.md` 的结论）。
- **价格**：未计算费用，不把 token 数当费用。
