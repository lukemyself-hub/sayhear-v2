# 消息引用与最终请求的一致性

日期：2026-10-24。问题：Luke 已接受删除后不再回看该消息原文，如何减少重复正文且不把当前内容误当作历史输入？停止条件：查清纯文本转换与消息可变性的主要边界，给出阶段 1 候选，不扩展实际工具执行。只读公开固定版本源码，不实现、构建或测试；本次两文件核查紧耦合，主 Agent 直接完成，无新增委派。

## 事实与已接受前提

- 基线仍为 `ai@7.0.153`，compatible 包 `3.0.78`，沿用前次版本核对，不宣称已安装或实施锁定。
- compatible 转换中，单个 user 文本 part 转为字符串 content；多个文本 part 可保留为内容数组。assistant 的多个 text part 会拼接为一个字符串。见[固定源码](https://github.com/vercel/ai/blob/ai%407.0.153/packages/openai-compatible/src/chat/convert-to-openai-compatible-chat-messages.ts#L210-L294)。因此不能只存一个 message_id 就声称已保存协议结构；结构和文本的读取、拼接方式也须记录。
- UIMessage 转 ModelMessage 时可过滤部分工具状态；assistant 内工具结果可形成独立 tool 协议消息，step-start 可分割块。见 [convert-to-model-messages.ts](https://github.com/vercel/ai/blob/ai%407.0.153/packages/ai/src/ui/convert-to-model-messages.ts#L61-L87)、[工具结果与块处理](https://github.com/vercel/ai/blob/ai%407.0.153/packages/ai/src/ui/convert-to-model-messages.ts#L352-L493)。一条 canonical 行不保证对应一条最终协议消息。合成工具是否进入实际请求仍归 M3，不由存储验收自动启用。
- ADR 0015 允许 generating 消息随输出更新，并禁止删除后的迟到内容写回；ADR 0010 的显式重试创建新 run/assistant 消息。已结束消息除删除外是否禁止改写正文，仍需把不变量明确写入方案，不能把现存文档当作已完整规定。
- ADR 0008 尚未决定中断回答是否用于新上下文，也未决定消息内部裁剪策略。引用方案不能擅自替 M3 选择。

## 调研时的推荐候选，后续已接受有限方向

后续状态（2026-10-24）：Luke 在行业核查后接受有限纯文本引用方向，见 ADR 0010；具体 JSON schema 与下文未决边界不因此自动收口。

阶段 1 的输入记录分为最终协议结构和正文来源。系统指令、当次时间、模型及生成参数等没有稳定消息行可引用的内容单独记录；稳定消息正文保存引用，避免每次复制。

允许引用的正文须来自已结束、成功持久化且未删除的消息。用户消息持久化后、assistant 完成或中断收尾后，正文不再普通改写；显式重试新建消息，删除仍按清空处理。该不变量只约束终态后的持久内容，不改变“Provider 完成但最终保存失败”可以发生的事实。恢复与正常收尾竞争、迟到 checkpoint 如何被拒绝由 M4/M2 细化。

引用记录不能只保留消息 ID。它还须覆盖最终协议位置、来源的 parts 范围和确定的拼接/包装方式。纯文本的候选示例是：某个最终 content 字段由消息 101 的第 0 个 text part 提供，另一个字段由消息 102 的若干 text parts 按原顺序直接拼接。记录消息内容的摘要以检测意外改写，不把摘要当正文备份，也不把摘要匹配当作 Provider 收到请求的证据。具体列、摘要格式和 JSON 结构未定。

在发送边界捕获最终请求体后，用本次已读取的消息内容与候选记录核对可还原的 JSON 内容、角色和数组顺序；核对成功并持久化记录后才发送原请求体。未来回看依据已记录的确定表示读取正文，不运行“当前 SDK + 当前配置”重新推算旧请求，也不以文字相同来猜来源。jsonb 不保留对象键或空白的字节布局，本阶段不追求 HTTP 字节级取证。

已删除来源显示缺失占位，不尝试恢复原文；未删除但摘要不匹配时标明记录无法准确还原，不展示新正文冒充旧输入。该校验本身不能保留丢失文字，因此终态不可改写仍是依赖，不能只靠 hash 弥补任意修改。

本次未确认让 generating 内容进入新请求。若 M3 确认需要使用变化中的内容或消息内部裁剪，须为当时选中的部分另定持久化表示，例如稳定前缀范围或带来源的片段，且删除后历史展示仍不得露出原文。不能直接引用会继续变化的整条消息，也不静默复制全文作为无条件回退。若输入形状超出可验证表示，须在发送前明确拒绝或重新设计，不能发送后才发现记录无法表达；具体失败体验由 M4/M5 确定。

## 取舍与未决

后续行业核查见[输入记录与行业实践](input-recording-industry-practices.md)。本文给出的是可行性候选，不是已经证实的行业通用做法；增量状态保存与外部内容引用仅支持部分原则，不能直接证明本方案已被广泛采用。Luke 要求先调研，尚未接受本方案。

相较每次完整复制，请求记录更多依赖稳定 canonical 正文，省下重复文本，代价是来源映射、终态写保护及缺失展示。尚未测量空间节省或执行开销。

强替代是重复保存每次实际内容，再为删除建立来源到副本的定位和清理。它较容易保存特殊转换，但仍重复占用正文；要满足删除后不显示原文，也不能忽略副本的来源和展示约束。

当前请 Luke 确认的是“已结束消息正文固定，以引用加最终结构和当次信息记录输入”的整体方向。未确认具体 JSON schema、M3 历史资格与裁剪、系统指令是否独立去重、并发发送与删除的事务顺序、SDK 升级迁移或任何实际运行通过。
