# 身份与权限学习记录

2026-10-22 至 2026-10-24 的设计讨论，尚无产品实现或验收。具体理解表现与缺口保留如下，不代表已掌握。后续从 [session.md](session.md) 的回访点接续。

- 回访点（继承阶段 0）：owner 隔离、续期写回 cookie 发生在哪一层、Auth 与业务授权的区别。
- 知识点 1「一次请求里 owner 从哪来、谁兜底」（2026-10-22，进行中）：已讲 cookie 携带签名令牌、服务端验签取用户 ID、客户端提交的 owner 不可信。Luke 自主提出由数据库兜底：按令牌中的用户 ID 只返回匹配数据（当次证据，方向对应 RLS）。已校准三处：浏览器不直达数据库，令牌由服务端转交；匹配对象是每行的 owner 列而非用户表；读取不匹配时静默过滤、写入不匹配时报错。新补关键前提：服务端若用绕过 RLS 的凭据，兜底失效，连接身份即决策点 1。
- 知识点 1 续「何时需要管理员凭据」：Luke 不确定，猜测"取历史封装上下文"属于此类（误判，把"服务端执行"当成"无用户身份"）。已校准判断标准：看操作是否发生在用户自己的请求内、代表谁，而非代码跑在哪。列举阶段 1 真正需要特权的操作：关闭注册下开通账号、账户清理删除 auth 用户、测试合成主体装载、每日备份；后续阶段的定时 Reflection。未确认，回访点：设计账户清理与流式 checkpoint 时请 Luke 判断用哪种身份。
- 知识点 2「事务归谁持有与数据库函数」（2026-10-22）：Luke 质疑“打包写入为何只是 A 的代价”（误以为 B/C 也须用数据库函数），已校准为“谁能持有跨多条语句的事务”。Luke 自主提出：函数与服务端分开发布，应保持薄而稳定的接口以兼容服务端迭代（当次应用证据，正确）；已补发布顺序与向后兼容追加。Luke 另问迁移 Neon 的可行性与函数测试方式，已答，耦合点写入 ADR 0009。未确认：是否理解 PostgREST 一请求一事务的机制，实施原子写时回访。
- 知识点 3「引用与外键」（2026-10-22）：Luke 问为何“挂在下面”还需要引用、同一消息能否多次 run。缺口：把示意树当成物理嵌套。已讲：表是平铺的，“挂在下面”即子行存父 id，外键是数据库核对该 id 真实存在并管删除传播；列出阶段 1 六类引用及数量，重试使一条消息多个 run，assistant 消息反向引用 run 说明是关系图而非树。当场回访：Luke 正确列出重试新增 run、attempt、输入快照、assistant 回答并给出引用方向，且指出用户消息不新增（应用证据）。缺口两处已校准：说成“消息引用两次 run”，方向反了，应为两个 run 各自引用该消息，消息行不记录 run；assistant 回答本身是消息表的新行。补充行数随结局变化：首次成功 4 行；fallback 后成功 6 行；两次首段失败 5 行且无回答；首段前停止 3 行。回访点：实施 schema 时再问引用方向。
  - 追问后 Luke 推出“run 同时引用用户消息与 assistant 回答”，第二个方向仍反（ADR 0010 定为 assistant 消息 → run）；另把回答是否存在归因于 attempt 成功。已校准：给出“后产生的行指向先存在的行”经验法则——run 在调用前已建、回答后出现，故回答指向 run，run 不回改；回答存在与否取决于是否出现过可见正文，中断/停止也保留部分回答，只有首段前结束才没有。仍未确认，实施 schema 时回访。
  - Luke 随后自主推出：消息表内按角色分两类，用户消息 run 列为空，assistant 回答 run 列必填（应用证据，正确）。已补：用 `role` 列区分而非两种类；该规则可由数据库检查约束强制；合成工具调用/结果同属某次 run；同表的理由是按时间顺序一次读出历史。
- 知识点 4「登出后旧令牌还能用多久」（2026-10-23）：已讲登出只删除服务端会话记录，access token 在到期前票面仍然有效；getClaims 只看票面，getUser 向 Auth 查证。Luke 复述选 A 时被盗 cookie 的路径：getClaims 认为有效、放行，再用令牌访问数据库（应用证据，主线正确）。已校准两处：getClaims 在我们自己的服务端本地验签，并不询问 Supabase；数据库层（Data API + RLS）同样只验签名和到期时间，所以两层都放行，这也是必须在入口用 getUser 的原因。另补充：cookie 里还有 refresh token，登出后无法续期，所以窗口最长约 1 小时。回访点：实施请求入口时，请 Luke 判断某个路由该用 getUser 还是 getClaims。
- 知识点 5「环境身份与迁移」（2026-10-23）：Luke 正确判断 URL 错但期望 ref 未改时由地址检查拦截、二者一起错时由库内身份记录拦截（当次应用证据）。已补身份记录需受保护，缺失或无法核实时中止。Luke 追问真实迁移场景，已结合首次建表、后续 Reflection、索引和权限规则变化讲解，区分日常业务写入与结构迁移；Luke 表示明白并确认三道护栏。回访点：实施时用合成配置演示两种误配，不连接真实用户库。
- 知识点 6「框架在哪一层续期与读数据」（2026-10-24，进行中）：用“打开聊天页→发送消息”的例子对照了 Next 和 React Router：发送链路两者相同（标准 Request/Response，入口要薄）；打开页面时，Next 拆成两层（Proxy 续期，Server Component 读数据），React Router 在 loader 里一处完成。Luke 回答“在 page.tsx 续期会怎样”：Server Component 写不了 cookie，所以续期无效，用户随后无法通过身份核验（当次证据，主线正确）。已校准三处：服务端续期本身成功了，失败的是新令牌送不回浏览器（官方模板会吞掉这个写入错误，所以没有报错）；当次请求不受影响，问题出在下一次请求；下一次浏览器带着已经用掉的旧 refresh token，结果取决于 10 秒复用宽限和 parent 例外，可能还能续上，也可能整个会话被撤销，表现为偶发被踢出登录，比“过期”更难复现。接着讲了哪些后续需求会拉开两者差距，然后请 Luke 决策。Luke 接受推荐，写入 ADR 0014。回访点：实施页面时，请 Luke 判断某段续期或读取代码应该放在 Proxy、Route Handler 还是 Server Component。
