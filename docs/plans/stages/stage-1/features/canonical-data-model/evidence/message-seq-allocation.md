# 会话内 seq 分配与展示顺序

日期：2026-10-24。目的：细化 ADR 0015 已接受的独立 seq，明确分配时机、并发提交与客户端排序。不重开是否使用 seq 的决定，不实现队列、跨设备实时订阅或消息配对布局。本次为小范围官方资料核对，由主 Agent 直接完成，无委派、构建或测试。

## 已核对的数据库机制

- PostgreSQL nextval 会并发安全地分配不同数字，但取得数字不等于事务已经提交；序列变化不随事务回滚，失败可能留下缺口。不能把裸 sequence/identity 当成提交顺序。来源：[sequence](https://www.postgresql.org/docs/current/functions-sequence.html)、[隔离级别中的序列说明](https://www.postgresql.org/docs/current/transaction-iso.html)。
- 对同一会话行取得冲突的行锁，可让后来的写入方等到前一事务结束；普通 SELECT 不因该行锁而被阻塞。行锁在事务结束或相应回滚时释放。来源：[行锁](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)。
- READ COMMITTED 下，每个查询读取其开始时的已提交视图，连续两个查询可能看到新提交的数据。来源：[READ COMMITTED](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED)。

以上支持下述分配算法，但不等于算法已在 Supabase 或产品实现中运行通过。

## 推荐候选，尚未接受

后续接受（2026-10-24）：Luke 明确接受 assistant 首段先入库确定位置再展示，已记 ADR 0015。下文关于该体验规则“待确认”的段落保留为推荐时的比较；锁后读最大值算法、客户端缓冲/补取和其他工程细节仍随完整规格审阅，没有运行通过证据。

seq 在同一会话内递增，作为首次提交到历史列表时确定的持久排序位置。用户消息首次入库时分配；阶段 1 assistant 在第一个非空正文出现时，以首段内容首次入库并取得 seq，提交成功后再向浏览器发布消息开始和首段正文。后续正文、checkpoint、终态保存及单条删除不改 seq。首次出现的工具/推理等未来情况不由此提前设计。

推荐保留会话表 id、owner_id、created_at 三列，按以下短事务分配：

1. 核验可信 owner 及会话归属，锁定对应会话行。
2. 取得锁后，再用单独查询读取该会话已存消息的最大 seq，包含已删除占位；为空则从 1 起步，否则加 1。
3. 将序号与新消息一起插入并提交。所有消息插入路径遵守相同分配规则；不能只在某一个 HTTP handler 加锁。

同会话后一个分配方须等待前一个提交或回滚；该推论依赖取得锁之后使用 READ COMMITTED 的新查询视图，不得把锁和 MAX 读操作随意合进同一旧快照的 CTE。其他隔离级别的行为需重新验证。账号清理等多对象写入须与 M7 统一锁顺序，以免死锁。

数据库负责分配并禁止既有 seq 普通改写，配合 owner+conversation+seq 唯一约束及 bigint 正值约束。最终用函数、触发器与权限怎样保证不可绕过，要在实际 schema 中明确，不能只靠客户端不传 seq 的约定。身份路径仍是 ADR 0009 的用户身份与 RLS，不因分配排序提升到特权身份。

MAX 查询需有按会话定位排序的索引。这里只持有新消息入库的事务锁，不跨 Provider 调用、不跨网络流生成，不在每个输出片段重新分配。未提交的号不对外发布；最终排序位置不因正文增长而改变。单条删除保留占位，因此不会因删除最后一条普通消息而复用它已提交的序号；账户整体清理不保留原会话排序空间。

## 替代与代价

- 会话行增加 next_seq 计数列，在事务中更新并分配：同样可串行化，并避免读取最大值，但需变更已接受的三列最小结构并维护计数与恢复一致性。若实际负载证明 MAX 读有问题再重评；本次没有性能测量。
- 表级 identity 并按 seq 排序：简单，但裸用不能保证同会话提交顺序；若再按会话加锁可限制同会话提交竞争，却仍是跨会话共享编号。本轮推荐改为会话内递增的具体分配方式，沿用已经接受的独立自增 seq 原则，不把此前 identity 推荐说成已实现。
- 首段先以临时位置显示、之后补入库序号：可避免首段等待数据库，但需要临时排序、补号及保存失败的合并逻辑。本轮推荐首段先落库，代价是首段显示多一次数据库等待；后续仍按流式 checkpoint 保存，不变成每个片段先写库再显示。

首段入库失败按持久化故障处理，不因为用户尚未看到正文而改走 Provider fallback。具体 run/attempt 失败映射及首段等待预算与 M4/M5 对齐；Provider 首段计时和浏览器可见首段耗时仍应分开记录。

## 客户端与证据边界

服务器只发布已提交新消息的稳定 ID 与 seq，浏览器按 ID 合并、按 seq 排序；流式更新定位同一消息，不按片段到达时间重排。刷新和历史分页按同样的服务端排序规则读取。未确认发送可保留临时发送状态，不把临时列表位置当持久排序事实。

网络可能先送达较大 seq，数据库提交顺序不等于浏览器收到顺序。合并时不能因见过最大 seq 就永久跳过迟到的较小 seq；发现当前已知历史范围的缺口时须保留补取路径，不无限等待缺号。分页边界之外的旧消息不按“缺号”盲目加载全历史。具体缓冲、补取与事件协议由 M4/M5 收口，本候选不增加跨设备实时同步功能。

seq 表示服务端确认进入历史的顺序，不保证不同设备同时感知的先后相同；也不证明某次模型输入包含哪些消息，仍以当次输入记录为准。若后续允许生成中继续提交，消息与其回答仍不强行相邻，本轮不因此授权队列。
