# 聊天请求按“正文开始前”与“正文进行中”分段设时间预算

Luke 于 2026-10-22 提出：模型已经开始输出正文时，不应被 SayHear 自设的 60 秒预算截断，应尽量等正文完成；60 秒内仍未开始输出正文，就直接结束，可有限次重试，最终失败时显示错误；达到 Vercel 300 秒上限被迫中断时，已显示内容保留，未显示的部分不再展示。Luke 同时认定，模型先思考几十秒才输出正文的体验不可接受，思考时长的限制须作为单独主题讨论。

单一的 60 秒总预算无法同时满足这两点，因此改为两段预算：

- **正文开始前**：从发出请求到首个可见正文片段，设首段截止时间。超时视为该次 attempt 失败，按 [ADR 0003](0003-provider-phasing-and-fallback.md) 与阶段 1 SPEC 的切换规则最多再试一次，仍失败则显示错误。思考内容不算可见正文。
- **正文进行中**：不再受首段截止时间约束，持续转发至完成。另设两项保护：连续若干秒没有新片段视为卡住，按中断处理；应用自设总上限略低于 Vercel 300 秒，由 SayHear 代码主动结束并保存已显示内容与运行记录，不依赖平台强制终止。

## 取舍与边界

首段截止时间与重试次数相乘，就是用户最坏的等待时间，例如 60 秒加一次切换最多等约 120 秒。这与“不能先思考几十秒”的要求冲突，首段截止的具体数值须在思考时长测量后确定，60 秒只作为上限起点。

Vercel 在 300 秒强制终止函数时，SayHear 代码没有机会收尾，浏览器已显示的内容可能未落库，run 可能停在进行中。应用总上限低于 300 秒，使中断仍是可控结束；所留余量与卡住判定秒数由阶段 1 实测确定。正文长度另由输出 token 上限约束。

客户端断开后 Vercel 函数是否停止、Provider 是否继续计费，官方未说明，仍为阶段 1 待测项。

## 失联运行的恢复与结果不确定性

Luke 于 2026-10-24 回复“认可，继续”，接受失联运行收口为中断，但无法确认的 Provider 结果保留 `unknown`。沿用 Issue #1 的恢复要求：后续读取发现超出可信执行期限仍无终态的 run，包括停在 created 的运行，将其恢复为 interrupted，记录未取得最终状态的原因，只保留已落库内容，不自动重新调用 Provider。显式重试仍创建新 run。

已有可靠 attempt 终态保留；缺少可靠结束证据时，Provider 最终结果记 unknown，不推定生成成功、失败、已经停止或停止计费。run 已收口和 Provider 结果未知可以同时成立，unknown 不表示应用继续等待。具体字段与状态命名随完整数据规格审阅。

该选择保留了证据的不确定性，代价是少数运行无法给出 Provider 的确定结果。相比将所有失联都记为 Provider 失败，它能避免把服务端崩溃或数据库写入丢失误归因给上游。可信执行期限须结合应用总上限与收尾余量，不能只凭刷新或暂时没有新内容判定失联；正常收尾与恢复竞争的原子条件更新、迟到写入及实际恢复验证由 M4 细化。

## 重评条件与恢复边界

真实链路显示正文阶段常超过数分钟，或 Provider 无法稳定区分思考与正文片段时，重评分段方式。
