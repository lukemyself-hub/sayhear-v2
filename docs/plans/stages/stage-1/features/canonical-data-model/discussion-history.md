## 表结构讲解与学习证据（历史）

后续决定（2026-10-24）：Luke 已接受输入快照存入 attempt 的 jsonb 列，见 [ADR 0010](../../../../../adr/0010-minimal-data-contract-and-owner.md)。下文知识点 7 的“初步倾向、待决定”保留为当时讨论，当前不再未定。原独立表建议被合并布局替代，删除副本与权限边界不变。

- 知识点 7「表结构：一对一关系何时拆表」（2026-10-24，进行中）：Luke 自己提出疑问：attempt 与输入快照为何要分开存，能否合并（属于主动质疑，方向合理）。已讲：fallback 时模型、参数、预算、格式都可能不同，所以快照应记在 attempt 这一层；两者是一对一关系，合并成一列在关系上成立。常见的拆表理由（大字段、单独保留期限、共用去重、不同查询）对阶段 1 都不够硬。初步倾向是把快照作为 attempt 的一列，待旧仓库调研回来，在 run/attempt 环节再请 Luke 决定。已提问：单条删除时快照中的消息副本会怎样，以及合并或拆表是否改变结果（正确答案：两种做法都会保留副本，删除语义不受影响）。Luke 答对了两种情况，并引用了 ADR 0010 的“不联动”规定（当次应用证据）。已校准一处：他把原因归于“在另一张表”；实际上副本是否保留由删除操作是否触碰快照决定，与拆不拆表无关。补讲两点：单条删除是修改（UPDATE）而不是删除行，所以不会触发 `on delete cascade`；快照必须存实际发出内容的副本，不能用消息 id 引用代替，否则回看时原文会丢失，并且快照不得作为后续输入来源（ADR 0005）。后一点待写入表结构 ADR。回访点：设计消息删除的实现时，问 Luke 为什么不会触发外键级联。
- 知识点 8「PostgreSQL 是什么、为何首选」（2026-10-24，Luke 主动提问，进行中）：已讲关系型数据库的基本形态，以及六个特性（事务、约束、RLS、函数、jsonb、扩展）分别对应 ADR 0009/0010 的哪些决定。核心观点：正确性由数据库保证，不只依赖应用代码。首选的原因：关系数据、灵活数据和向量检索可以放在同一个库；托管生态好（Supabase 建在它之上）；标准开源，便于迁移；成熟。和 MySQL（无原生 RLS）、MongoDB（不强制跨记录约束）、SQLite（不适合多实例服务）做了对比。代价：写入扩展有上限、连接数有限、规则写错也会被严格执行。已提问：换成 MongoDB 后，同 owner 引用规则由谁保证，有 bug 时会怎样。Luke 答：规则只能写在应用代码里；代码有 bug 时，run 和它引用的消息可能分属不同用户（当次应用证据，正确）。已补两点：这类 bug 不会报错，数据悄悄写错，发现晚、清理难；即使有 RLS，外键检查也会绕过 RLS，所以 Postgres 里也必须靠组合外键，不能只靠 RLS（ADR 0010）。
- 决策点 6 第 1 环「通用约定」（2026-10-24，已讲解，待 Luke 决定）。推荐如下：
  - id 用 UUIDv7：数据库默认生成；需要提前知道 id 时（如 assistant 消息）由服务端生成后传入；Supabase 是否内置 `uuidv7()` 实施时核实。客户端传来的消息 id 不作主键，只用作幂等键。
  - 时间一律用 timestamptz，由数据库填 created_at；日期归属规则留给日期导航功能。
  - 自定义状态用 text + CHECK；SDK 或 Provider 的原始值存为 text，不加 CHECK。
  - 消息按 created_at 加 id 排序，前提是有先后关系的消息不在同一事务里写；实施时加测试，确保回答排在问题之后。
  已提问：为什么 finishReason 不加 CHECK，而自定义状态要加。
  - Luke 2026-10-24：同意 UUIDv7、timestamptz、自定义状态用 text+CHECK、外部原始值存 text（前三条已定）。他的回答：SDK 字段会随升级变化，加 CHECK 会带来维护成本；这些字段只用于验收和排查（当次证据，主线正确）。已校准：加了 CHECK 的后果是升级后写入直接失败，而不只是维护成本；应用逻辑若要依赖它，须先映射到自定义状态列，原始值另列保存。
  - 排序方面，Luke 质疑：基础约定不应在将来支持多用户时被迫修改。已校准前提：排序限于同一会话，多用户本身不破坏时间排序。但这个质疑揭示，原推荐依赖“有先后关系的消息不在同一事务写入”这一隐含前提，而 ADR 0010 的合成工具调用/结果消息、多设备并发都可能打破它。推荐已改为自增 `seq` 列（generated always as identity）专用于排序，created_at 只用于显示和日期。已说明边界：序号在插入时分配，不保证提交顺序，影响将来的增量同步，但不影响阶段 1。待 Luke 确认。
  - Luke 再次质疑：“时间相同”的并列不是已经可以用“时间 + id”解决吗？承认上一轮论证缺了一环。补充：按 id 兜底要求 id 顺序等于写入顺序，而 UUIDv7 记录的是生成时刻；assistant 消息 id 需要在流开始前提前生成，加上服务端与数据库两种生成器时钟不同，同一事务里写入时，工具调用和结果可能排到回答之后。改立规则也能做到，但这条规则刚定就要开例外，还会把排序和 id 生成方式绑在一起。仍推荐 A（加 seq）；B（时间 + id + 明确的生成规则与测试）也可行。**Luke 2026-10-24 选 A：加 seq 自增序号列专用于排序。通用约定四条已全部定下，待与各表一起写入表结构 ADR。** 学习证据：Luke 能检验推理链是否完整，找出“前提不足以推出结论”（当次证据）。
