# 每次模型请求显式提供有效产品指令

Luke 于 2026-10-24 在讨论 Tolan 每轮重建上下文、系统指令与数据库记录的区别后回复“好，没问题，继续”，认可每次请求携带指令。随后针对仓库内独立指令文件随应用部署的建议回复“认可这个决策，继续”，接受该来源及修改规则需要重新部署的取舍。再回复“没问题”确认阶段 1 不保留独立 system 聊天记录。版本机制仍待确认。

## 决定与依据

2026-10-24 输入保留更新：ADR 0005 已确认删除消息后旧运行详情不再显示其原文。本文下述实际副本契约在这一删除场景中放宽，消息引用表示由 ADR 0010 继续细化；不能仍承诺删除后永久完整回看。每次请求的有效产品指令、同一 run 固定指令与不从旧输入记录构造新上下文的决定不变。

- SayHear 在每次独立模型请求中明确提供本次有效的产品指令，包括 fallback 请求，不依赖上一请求自动保留规则。未来工具多步也须检查每次实际请求的有效指令，但不因此将实际工具执行提前到阶段 1。
- 每次发送有效指令与每轮新增一行系统消息是不同操作；前者不要求后者。阶段 1 不设独立 system 聊天消息行，详见下文。
- 沿用 Issue #1 与 ADR 0005 的实际输入副本契约，输入快照保留本次实际发送的系统指令及其余输入，不以指令版本标识或消息 id 替代实际副本，也不从旧快照构造新上下文。

原因是每次重新组装或裁剪上下文时，仍应明确保留产品身份、回应原则与边界。显式提供指令便于检查是否遗漏，并不保证模型每次遵循；产品行为仍需后续场景评测。外部依据及证据边界见 [Tolan 定点核查](../plans/stages/stage-1/features/canonical-data-model/evidence/tolan-per-turn-context-and-system-instructions.md)。本文不新增 Provider 参数名假设，SDK 与 Provider 映射在实施时按锁定版本核实。

## 已接受的指令来源

阶段 1 从仓库内独立文本文件读取产品指令，随应用部署。修改规则需要重新部署。该决定不要求每轮把文件内容另存为消息行；每次实际请求仍按上述契约保留实际输入副本。

| 方案 | 适用需求与代价 |
| --- | --- |
| 仓库中的独立文本文件，随应用部署 | 已接受。规则变更随代码审阅与版本管理；修改生效需要重新部署。文件路径、格式及运行详情版本字段尚未确定 |
| 数据库中的专门指令配置与版本记录 | 已考虑，阶段 1 不采用。适合需要独立于部署更新指令的场景；需明确编辑、发布、生效、权限与回退机制，不应直接以聊天消息表承担配置职责 |

采用文件方案的理由是阶段 1 尚无在线编辑指令、按用户定制规则或独立发布指令的已确认需求。先随部署维护可减少需理解和维护的配置流程；不因此锁死未来数据库管理方案。当前不创建实际 prompt 文件，不撰写完整人格指令，不设计配置表或管理界面。

文件路径与格式、版本标识的具体实现仍为待审阅建议。同一 run 多次尝试的选择规则已接受，见下文。消息表沿用 ADR 0010/0015 的 owner、来源和删除约束，不能由本 ADR 推定新的表结构。

## 同一 run 固定产品指令

Luke 于 2026-10-24 回复“认可，继续”，确认产品指令更新从新 run 生效，同一 run 的主路线与 fallback 固定使用开始时选定的指令内容。fallback 不重新读取并选择另一版本；显式重试创建新 run，因此可以使用新版本。

这里固定的是产品指令内容，不要求不同 Provider 的协议请求体相同。各 attempt 仍分别保存 SDK 转换后的实际输入副本，版本标识不能替代副本。该决定也不表示 fallback 的全部历史选择、日期等上下文字段已确定，相关契约继续由 M3/M4/M6 细化。

相较于每次 attempt 重新选择最新指令，固定内容能避免一次运行在切换 Provider 时同时改变产品规则，便于解释和排查。代价是更新不影响已开始的 run；若未来需要紧急撤销旧规则，须另外设计停止或撤销机制，不能假定部署更新会改写进行中的运行。

版本追踪的常规实现建议为：独立 UTF-8 文本文件保存指令，以文件内容的 hash 标识版本，部署版本定位应用代码，每次实际输入快照保存完整发送内容。hash 用于比对内容，不用于还原指令，也不证明模型遵守规则。具体路径、摘要算法及存储列随完整规格审阅，本段不将这些细节标为 Luke 已逐项确认。

## 历史裁剪与旧指令原文保留

Luke 于 2026-10-24 再次明确：上下文过长时可以裁掉更早的 user/assistant 历史，但每次请求必须携带有效产品指令；即使后来部署指令 B，旧运行的输入记录仍须保留并可读取当时 A 的原文。指令不能和普通历史一起按时间裁掉，也不能只保存版本号或 hash 后回读当前部署文件。该约束同样适用于 fallback；各 Provider 的实际协议映射仍按已定范围核对。

指令正文可按同一 run 的固定记录保存，各 attempt 指向该记录并保留本次实际协议表达，不要求为了“快照保留”逐 attempt 重复一份相同正文。消息删除不清空这份产品指令记录。账户清理仍遵守 ADR 0010，不把原文保留解释为永久不可删除。

预算处理的工程建议：先为必需指令和输出留出预算，再按 M3 策略选择可容纳的历史；最终请求不能容纳必需指令时，在发送前明确失败，不静默删减产品指令。具体 token 估算、当前提问的保留策略、历史裁剪单位和失败展示仍由 M3/M4/M5 细化。本轮没有实现或测试证据。

## 不保留独立 system 聊天记录

阶段 1 不生成、不装载独立的 system 聊天消息行，也不为它增加创建入口、历史选择或专用展示逻辑。产品指令来自已接受的部署文件，每次实际请求的指令内容随输入快照保存，运行详情从快照读取。历史快照继续禁止回灌新上下文。

Luke 追问真实聊天何时会产生 system 记录。已澄清当前聊天不需要独立 system 消息行；此前保留它只服务于合成验收，而那项验收的目的由实际请求链路覆盖。原验收要求系统指令有位置且可保存、检索、展示，来源是阶段 0 [原始提纲](../plans/stages/stage-0/evidence/stage-0-data-and-delivery-evidence.md#合成数据与验收责任)，该提纲没有固定消息表或独立行。现在改用非私人测试指令核对：普通请求和实际发生的 fallback 请求均携带指令；历史预算裁剪后指令仍保留；保存的实际输入副本包含完整指令，刷新后可在对应 attempt 的运行详情读到。核对的是发送、保存、读取与展示，不把模型某次回答符合规则当作链路正确的证明。恶意历史指令仍保留普通用户角色，验证组装没有把它提升为系统指令。

代价是阶段 1 不提供历史 system 消息的导入或对话中途指令事件能力，目前没有已确认需求。若将来出现会话专属规则、规则事件或导入需求，再按真实场景决定结构。该决定不涉及合成工具记录的取舍。

## 重评条件

需要无需部署即可发布规则、不同用户采用不同规则、正式的提示版本实验，或 Provider 间的指令表达差异影响产品行为时，重评来源与版本管理。每次实际请求的输入仍须可追溯。
