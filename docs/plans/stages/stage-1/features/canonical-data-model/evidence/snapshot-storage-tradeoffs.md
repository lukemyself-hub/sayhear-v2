# 快照正文重复与消息引用的存储取舍

日期：2026-10-24。问题来源：Luke 接受发送前保存后，意识到完整请求快照会重复保存近期消息，要求重新核对是否值得。只做文档核查与假设算术，不执行产品测试、连接数据库或创建资源。

## 能确定的结论

完整请求副本重复保存历史内容，增加的是每次所选上下文，不一定是全部聊天历史。增长取决于每次请求大小、调用次数、fallback 次数和保留期限。固定窗口时大致随调用次数累积；不能把“每次都带完整历史”的无界增长模型直接套用到已有预算裁剪方案。

仅保存消息 ID 与顺序，通常会比再次保存长正文小，但引用本身不是正文备份。按目前删除时清空消息 parts 的决定，被删消息无法再从该行还原；即使消息未删除，只凭 ID 也没有保留系统指令、参数、时间注入、裁剪与 Provider 转换后的实际表达。来源引用可证明选择了哪个记录，不能独自证明请求的完整内容。

若允许删除后历史运行详情也不再提供被删原文，可采用引用加必要请求元数据的较轻记录，但不再满足此前“完整实际输入可永久回看”的要求。必须明确标为重建或缺失记录，不能仍称无损实际请求快照；该变更涉及 ADR 0005/0010/0016 与 Issue #1 运行详情契约，尚未接受。

若仍要完整历史回看，可保存不可变的最终输入内容块，每份相同内容在 owner 内复用，attempt 内保存有序引用和本次独有字段。引用必须指向留下来的实际内容，不能只指向会被清空的原消息。最终请求须可无损还原，包括 Provider 特有转换和参数；字段和引用本身也有开销。该方案以更多关系、来源映射、owner 隔离、账户清理及无引用内容回收逻辑换取去重，不是仅把 ID 填入现有列。

单独建立快照表并仍保存每次完整请求，并不能消除跨请求正文重复。真正去重可能使内容块表有必要，这属于新存储需求，不是恢复此前一对一快照表的充分理由。

## 假设量级示例，不是测量

假设 1,000 次成功对话，每次新增用户与 assistant 正文合计平均 2 KiB，每次请求快照平均 20 KiB。则新增正文约 1.95 MiB，快照约 19.53 MiB，合计约 21.48 MiB。快照内容约为新增正文的 10 倍；这不是整个数据库占用倍率，也不是费用预测。

示例忽略索引、行与 JSON 开销、数据库压缩、备份、fallback 和引用存储成本；实际上下文尺寸与系统指令可能显著改变结果。PostgreSQL 对较大字段可使用 TOAST 压缩或行外存储，但不能据此假定重复内容在不同快照行间自动共享。来源：[PostgreSQL TOAST 官方文档](https://www.postgresql.org/docs/current/storage-toast.html)。本文不推算压缩比例。
