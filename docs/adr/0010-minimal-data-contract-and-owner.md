# 阶段 1 最小数据契约：每张产品表直接带 owner，跨表引用同 owner

在 [ADR 0009](0009-server-data-access-and-rls.md) 的 RLS 路径下，确定哪些记录归属于谁、归属如何约束、删除如何传播。只固定行为契约，物理表名与完整列在实施时提出。Luke 于 2026-10-22 确认。

## 决定

- owner 即 Supabase Auth 用户 ID（`auth.users.id`），不另建应用账号表。阶段 1 不需要账号级产品属性；以后需要时再加，不影响已有 owner 列。
- 阶段 1 的 owner 作用域产品表为连续会话、消息、run、attempt，各表直接带 `owner_id`，RLS 策略逐表比对本列，不通过连表推断归属。输入快照存于 attempt 的 `jsonb` 列，直接受该行的 owner 与 RLS 保护，不另建快照表或快照专用 owner 列。消息中的工具过程沿用 [ADR 0015](0015-message-parts-and-ordering.md) 的 parts；按 [ADR 0016](0016-per-request-system-instructions.md) 不设独立 system 聊天行。
- 跨表引用同时带 owner：子记录引用父记录时以 `(owner_id, 父 id)` 组合外键约束，保证两者同属一人。原因是 Postgres 的外键检查绕过 RLS（Postgres 文档 Row Security Policies 一节），仅凭 RLS 无法阻止把自己的 run 挂到他人消息上。只在真实存在的引用上使用，不在无引用的表上冗余铺设。
- 阶段 1 的引用关系与数量：

  | 引用 | 数量 | 用途 |
  | --- | --- | --- |
  | 消息 → 会话 | 一个会话多条消息 | 连续会话容器 |
  | run → 触发它的用户消息 | 一条用户消息可有多个 run（显式重试各为新 run，传输重发不新增） | 重试不覆盖旧回答 |
  | attempt → run | 一个 run 最多两个 attempt（主路线 + 一次 fallback） | 追溯真实路线 |
  | assistant 消息 → 产生它的 run | 一个 run 至多一条 assistant 消息；首段前失败则没有 | 来源链：回答 → run → attempt → Provider/模型 |
  | attempt 内的输入快照列 | 每次请求的输入记录，按本文 M2 首版引用表示，不是独立快照子行 | 运行详情 |
  | 以上产品表 → `auth.users` | 每行直接关联 owner，快照列随 attempt 行清除 | 账户清理级联 |

- 幂等：run 以 `(owner_id, 客户端请求标识)` 唯一。
- 账户清理：各表对 `auth.users` 外键 `on delete cascade`，由特权通道删除 auth 用户后数据库一次级联清除。
- 单条删除：消息保留一行作为“该消息已删除”占位，带删除时间，**清空行内原文**；历史选择排除已删除消息；按更新后的 ADR 0005，历史运行详情不再显示该消息原文，保留来源标识与缺失说明；不级联删除其 run、attempt 或整份输入记录。

## 输入快照与 attempt 合并存储

Luke 于 2026-10-24 回复“看上去没问题，我同意”，接受输入快照存入 attempt 的一个 `jsonb` 列，不另建一对一快照表，并要求同步相关文档。本节取代此前独立快照记录的结构建议；既有“输入快照按 attempt 归属”是逻辑关系，不再解读为必须存在一张子表。

此前要求每个实际请求保留完整副本；现按下文更新，已删除消息不再保证原文回看，消息内容的引用表示正在细化。仍须从 SDK 转换后的真实请求确定内容与顺序、系统指令及必要时间和工具定义，不能把组装前 ID 列表冒充最终输入；不保存请求头与密钥。主路线和 fallback 分别保留各自实际输入，不因共享产品指令而合并快照。快照只供 owner 回看排查，不作为后续上下文来源。列名、JSON 结构、未发送或捕获失败时的表示，以及发送与保存时序仍需 M2/M4/M6 细化；有快照本身不证明 Provider 已收到请求。

快照合并时尚无独立保留期限、权限或多版本生命周期需求；后续重复正文的存储关注点已触发表示方式重评，见下文。合并后少维护一组独立行、外键及 RLS 策略，常规运行列表按需选择列，展开详情再读取快照。该选择不宣称已测得存储或性能收益。

单条消息删除清空该消息内容，历史运行详情不再显示其原文，但保留 attempt 及其输入来源记录；引用读取、潜在内嵌正文的处理与删除竞态需由 M2/M7 对齐。整账户清理仍随 attempt 行一起清除行内输入记录。跨主体读取验证须覆盖 attempt 的快照列，不能因不再单独建表而省略。来源标识与必要本次信息如何对应实际请求须在发送边界核对，不能只凭选中消息的 ID 列表声称已完整记录最终请求。

若以后一个 attempt 承载多次独立模型请求，或快照需要独立权限、保留期限及实际数据规模证明确需分离，重评一列的布局。未来工具多步可能改变请求与 attempt 的关系，届时决定按请求拆分或其他结构，不预先把执行能力加入阶段 1。

## 发送前保存门槛与存储重评（2026-10-24）

Luke 在完整数据流讲解后明确接受“第四步”：捕获 SDK 转换后的最终请求体，先完成快照保存，成功后检查取消与剩余预算，再转交网络；保存失败不发送、不触发 Provider fallback。依据见[捕获时序证据](../plans/stages/stage-1/features/canonical-data-model/evidence/request-snapshot-capture-timing.md)。这是设计接受，尚无运行验证；保存成功不证明 Provider 收到请求。

Luke 随后提出重复保存历史正文可能使存储显著增加，要求 double check 能否仅引用消息 ID。该新关注点重开了完整副本的物理表示；Luke 随后明确接受删除单条消息后旧运行详情无法再显示该原文，已同步 ADR 0005，取代此前删除后仍保证完整回看的要求。后续已接受有限引用方向，见下节；具体引用字段尚未收口，不能跳过设计直接冻结 schema。发送前保存原则已接受，具体保存表示须与重评结果一致。

下一设计优先评估引用消息及保存本次独有输入信息的轻量方案，不再为了被删原文回看增加不可变正文存储。该有限方向已在行业调研后接受；最终输入保真、生成中消息变动及引用映射仍须完成相应规格和验证。每次完整副本与不可变内容块保留为替代方案；不可变内容方案须保存最终输入的实际内容和顺序，不能用日后重新转换消息来冒充原请求，也引入内容块存储、owner 隔离与清理管理。单纯把完整快照搬到独立表不能减少正文重复。当前没有实际数据规模、压缩后数据库占用或成本测量，不以假设倍率认定应改选方案。详见[存储取舍核对](../plans/stages/stage-1/features/canonical-data-model/evidence/snapshot-storage-tradeoffs.md)。

## 已接受：有限范围的稳定正文引用与当次请求结构

Luke 在完成行业调研后明确回复“同意，保留引用方向，限定功能，不提前建设复杂工具和场景”，接受阶段 1 的有限引用方向。接受的是针对已选 SDK/Provider 纯文本请求的正文引用与当次结构记录，不是支持任意工具、多模态和 Provider 的通用请求重建系统。具体 JSON 字段、边界竞态和异常处理仍需细化。此前先调研再决定的过程见[一手资料核查](../plans/stages/stage-1/features/canonical-data-model/evidence/input-recording-industry-practices.md)表明：外部内容引用和增量状态保存有公开依据，逐次完整记录输入同样有明确实践；不能把当前组合称为通用架构。该候选的理由应是 SayHear 的存储与删除取舍，仍需承担来源映射、终态写保护和 SDK 变化的验证成本，该接受依据是 Luke 对本项目成本、删除与维护负担的取舍，不将其称为行业通用架构。

引用方向以已结束并成功持久化的稳定消息正文为适用前提，终态后除删除外不再普通改写；重试仍新建消息。attempt 内记录最终协议结构、正文来源与确定的读取/拼接方式，另存系统指令、当次时间、模型参数等本次信息。发送边界须核对这些记录能表达当次实际请求，成功保存后才转交网络；不在以后调用新版 SDK 重算并冒充旧输入。

来源删除后显示缺失；未删除但正文校验不符时如实标记无法还原，不显示新正文冒充历史输入。变化中消息是否可选、内部裁剪及特殊转换的表示方式仍待 M3/M4/M6 对齐，不因引用存储顺带决定。该整体方向已接受；上述待定项不被本次接受自动裁定，详见[事实、推荐与代价](../plans/stages/stage-1/features/canonical-data-model/evidence/message-references-and-final-input.md)。

## 输入记录的字段草案，待完整规格审阅

格式版本建议：每份 input_record 内有独立 `schema_version`，首个落地格式从 1 起；它标识正文引用、顺序、字面内容与转换表达的读取规则，与消息行 `parts_schema_version` 分别演进。应用/SDK 版本用于定位实现来源，不替代这两个格式标识。未知格式不能按最新规则猜读；未来升级时再决定实际需要的迁移或读取转换，不在阶段 1 预建通用兼容层。消息 parts 变更若影响旧输入引用，须作为同一个升级问题处理，见 ADR 0015 的版本建议。

记录仍存于 attempt 的 jsonb 列。建议包含表示格式版本、按实际协议顺序排列的消息结构、各正文位置对应的消息 ID/parts 范围及确定的拼接方式、来源正文校验信息、实际系统指令与本次注入时间信息、模型与生成参数。SDK/适配器版本和历史选择理由在对应 run/attempt 元数据中记录或引用，不重复建立一套真源。具体字段名和布局由 M2/M6 汇总审阅，不逐字段要求产品表决。

本次实际参数若为省略或未知，保留其区别，不猜测 Provider 默认值。消息角色、数组/字符串结构、顺序和文本拼接方式以捕获的最终请求为准；来源归属不能只凭相同文字匹配。若系统指令含会变化的日期等内容，须记录实际注入部分，不能只有文件 hash。系统指令内容的跨 run 去重不作为本阶段前置。

正文引用应只从已认证 owner 的 canonical 记录解析。删除标记优先于从内存或缓存回看的正文，已删除显示缺失；未删除但校验不符显示无法准确还原。仅凭当前消息的 seq 排序不能推断当时输入顺序。SDK 升级后的读取遵守记录的表示版本，不重新调用当前 SDK 猜测旧请求。

该草案不自动选择 generating/interrupted 历史的资格、内部裁剪、删除与发送的生效顺序、超出支持形状的用户体验或最终失败状态；相应 M3/M4/M7 契约仍未收口。合成工具记录仍按已定存储验收，不意味着实际工具执行或工具历史发送已获范围授权。

## 已接受：JSON 来源由数据库强制校验

Luke 于 2026-10-24 明确同意“保留 attempt 内的 JSON 引用，由数据库强制校验来源，暂不新增引用关系表”。沿用 attempt.input_record 的 jsonb 布局，以数据库触发校验覆盖输入引用写入，不只依赖服务端约定或 attempt 本行 RLS。来源须存在、与 attempt 同 owner、属于 run 对应会话，part 类型及范围须合法；目标会话从 run 的触发消息推导，不信任 JSON 自报归属。普通更新不得通过改挂 owner/run/会话关联绕过校验。

相比额外引用关系表，该方案少维护一套关系行，代价是承担 JSON 格式解析和数据库校验维护。若按来源反查成为实际需求或校验复杂度明显增长，再重评关系表。具体触发器、权限、版本解析与并发行为尚未实现或验证；该决定不解决删除与发送的生效顺序，也不冻结全部 JSON 字段。候选细节见 [run/attempt 草案](../plans/stages/stage-1/features/canonical-data-model/run-attempt-draft.md)。

## 已接受：run 的完整状态集合

Luke 于 2026-10-24 回复“认可，继续”，接受 run 的五个状态，结束原因另列：

| 状态 | 语义 |
| --- | --- |
| created | 已登记，尚未开始执行 |
| running | 正在准备输入、调用 Provider、切换备用或保存收尾 |
| succeeded | 正常生成完成，且必要保存成功 |
| failed | 明确失败，包括输入记录保存失败、首段前最终失败或最终保存失败 |
| interrupted | 用户停止、正文生成中断，或失联后的恢复收口 |

主 attempt 失败而备用成功且保存完成，run 为 succeeded；用户在首段前停止仍为 interrupted，不建空回答；Provider 正常结束但最终保存失败，run 不得为 succeeded。Provider 结果未知不增加 run 的 unknown 状态，也不使 run 无限保持 running。缺少可靠终态的恢复语义沿用 ADR 0006。

该接受不等于全部状态转换和并发优先级已确定：停止与正常完成竞争、停止后保存又失败、恢复与迟到收尾、事务失败时可持久化哪些状态等，由 M4 汇总明确并验证。不能在数据库不可写时声称失败状态一定已成功保存。

## 已接受：attempt 生命周期与 Provider 结果分开

Luke 于 2026-10-24 回复“认可，继续”，接受 attempt 生命周期为 created / running / finished，另列 Provider 结果 not_sent / succeeded / failed / unknown，结束原因另存。Provider 结果在未收口时为空，finished 必须有结果；具体列名尚未确定。

- created：已建记录，正在准备请求或保存输入，尚未越过持久化的发送前门槛。
- running：已越过发送前门槛，进入本次网络调用阶段；该标记仍不证明 Provider 已收到。
- finished：本地不再等待或继续这一尝试，包含正常完成、明确错误、用户停止、超时及恢复。finished 不保证远端已经停止，也不等于整个 run 保存成功。

结果 not_sent 仅在有可靠依据确认未调用网络发送时使用；缺少发送时间戳、未收到响应或看到已保存输入，都不能单独证明未发送。succeeded 表示观察到正常完成；failed 表示观察到明确的 Provider 错误响应或错误终态；unknown 表示未取得可靠的最终结果，不能据此推定计费或远端已停止。

首段超时是本地已知的调用失败原因，但远端生成结果可能 unknown；超时后是否 fallback 继续依据结束原因、是否已有正文、剩余预算及已定切换规则判断，不单凭 Provider 结果枚举决定。用户在发送前停止可为 finished/not_sent，发送后停止而没有可靠 Provider 终态则为 finished/unknown；run 都按已定规则记 interrupted。

这比让 attempt 完全复用 run 状态多一个结果字段，换来对“调用未发出”和“调用已收口但远端结果不明”的明确表达。发送前状态的持久化顺序及 M4 竞态仍需完整规格与验证。本次接受这套分列语义，不表示完整状态转换、数据库约束或异常路径已实现。

## 已接受：发送资格与结束结果的原子写入

Luke 于 2026-10-24 回复“没问题，继续吧”，接受将保存输入记录与有条件的 created→running 更新放在同一次数据库操作中，只有确认该操作成功取得资格的执行方才继续发送；同时接受 finished 与 Provider 结果一起保存。running 不证明真实送达，崩溃后结果不明不自动重发。以下是具体约束与尚待完整规格审阅的实施细节，本次不代表代码已实现或验证：

- created/running 的 Provider 结果为空，finished 必须有四种结果之一；以数据库 CHECK 约束非法组合。结束原因和结束时间随收口原子写入，不能先把状态设为 finished 后再补结果。
- attempt 不从 finished 回到 running。created 可直接收口为 finished，例如发送前停止；running 可收口为 finished。新的尝试必须是符合既定次数和 fallback 规则的新 attempt。
- 建议在同一个受 owner 与 RLS 约束的数据库操作中，保存本次最终输入记录并有条件地将 attempt 从 created 转为 running；只有确认该操作成功取得执行资格的调用方，才能继续转交网络。其余重复执行方不重复调用 Provider，按既定幂等处理。
- 该数据库函数只处理持久化、条件更新和幂等，不调用 Provider 或在数据库事务内等待网络。SDK 与流重试保持已定关闭状态，不能绕过单次发送门槛。
- running 是本地已取得发送资格的标记，不是已送达证明。数据库操作结果不确定时不转交网络；若实际提交了 running，恢复时仍可能只能记录 unknown。确认操作成功后、网络调用前也可能崩溃，恢复不能凭 running 或缺少响应推定 not_sent。
- 调用方仍须在转交网络前检查取消和期限。若它能确认自己尚未调用发送函数，可按 not_sent 收口；崩溃后丢失这一局部事实时，恢复按已有证据保守判断，不自动重放。终态收口与迟到回调竞争的细节继续由 M4 决定。

这套建议避免把“数据库提交”和“Provider 收到请求”误作一个共同事务。时延、并发重复提交、数据库提交成功但响应丢失、崩溃间隙与超期恢复须由后续构建流程验证，本轮不执行测试。

## 其他数据边界的重评条件
