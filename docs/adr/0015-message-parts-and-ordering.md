# 消息采用 AI SDK parts，使用独立 seq 排序并保留产品状态

Luke 于 2026-10-24 确认消息采用 AI SDK parts、保留 seq 排序，并在阶段 1 继续自建库内运行记录。本 ADR 固定已经达成共识的通用约定和消息存储选择，不表示完整 schema 已设计完成。剩余讨论见 [canonical 数据结构接续](../plans/stages/stage-1/features/canonical-data-model/session.md)。

## 决定

- 消息内容使用 AI SDK 的 parts，存于 jsonb，不提前定义 SayHear 自有 parts 或建立双向转换层。SDK 版本在实施时锁定。持久化格式识别需要可追溯，但具体版本字段尚未决定。
- 消息的 owner、身份、run 来源关联、删除与生成状态使用 SayHear 管理的列，沿用 [ADR 0010](0010-minimal-data-contract-and-owner.md)。选择 parts 不自动改变其来源与数量契约。
- Luke 在后续讨论中确认行粒度与 run 关联：每条用户输入各一行，role=user，不填写 run_id；run 引用触发它的用户消息，允许显式重试产生多个 run。一次 run 的 assistant 输出聚合为一行，role=assistant，run_id 必填且唯一，一个 run 至多一条 assistant 消息；首段前失败仍可没有消息。
- 一次 assistant 输出内的文本、工具调用与结果，以及未来启用后的可见推理，存于同一行的有序 parts。工具调用与结果可由同一个工具 part 的输入、输出及状态表示，不为每个工具步骤另建聊天消息行。存储行粒度不限制界面展开方式，也不要求与 Provider 协议消息一一对应。系统记录的具体角色规则与合成工具验收方式仍待讨论。
- id 使用 UUIDv7。通常由数据库生成，需要提前知道时由服务端生成；客户端 id 仅用作幂等键，不直接作为数据库主键。目标数据库是否内置 uuidv7() 实施时核实。
- 时间使用 timestamptz。自定义状态使用 text + CHECK，SDK 或 Provider 的原始值不以 CHECK 穷举；应用需要据此分支时，先映射到自定义状态。
- 消息使用自增 seq 专用于稳定排序。按消息出现顺序展示，用户消息和对应回答不必相邻，流式更新不重新排序。预生成 id 不等于提前占据展示位置。identity 不保证并发事务提交或网络到达顺序，序号分配与客户端合并规则须在实施规格中细化。
- 消息生成状态采用 generating、complete、interrupted，与 deleted_at 独立。Luke 后续确认删除清空与并发保护：parts 必须为 JSON 数组，不允许 SQL NULL；删除时在同一事务中将 parts 置为 [] 并设置 deleted_at，保留消息身份、seq 与来源关联。数据库约束 deleted_at 非空时 parts 必须为 []；其他承载内容的消息列也须清空。历史快照保留边界继续按 ADR 0005/0010。
- 所有流式与最终内容保存均须在原子更新中检查 deleted_at 为空，已删除则跳过内容更新；不得先查询再无条件保存，也不得通过普通生成保存清除 deleted_at。数据库清空约束与条件更新共同防止迟到写入恢复内容。生成中删除是否同时停止运行仍未决定。
- 阶段 1 不接外部观测工具，沿用 [ADR 0005](0005-chat-experience-and-run-record.md) 的库内运行记录及不向第三方观测平台发送内容的边界。未来接入可从新运行开始，不强制迁移全部历史；历史导入能力、缺失信息与成本届时评估。

## 合成网络搜索记录的验收边界

Luke 于 2026-10-24 指定网络搜索为合成工具场景，并回复“没问题，继续”确认三类样本与验收边界：用户询问事实，assistant 发起搜索，工具返回结果，assistant 给出回答；另覆盖搜索失败、已有调用但尚无结果的情况。

阶段 1 只验证上述合成记录的保存、读取及运行详情展示，不执行真实搜索、自动续跑或新增完整工具交互界面。用户输入单独一行，assistant 的文字、工具调用与结果按既定行粒度保留在该行的有序 parts 内。样本须保留调用与结果的关联，失败或缺失结果不得伪装成成功；具体 SDK 字段和状态按实施时锁定版本核对。所有查询与结果内容明确标为合成数据，不冒充真实检索证据。

选择网络搜索是因为 Luke 判断它更可能成为较早加入的工具能力；不据此承诺实际执行的实施阶段。是否将这类历史纳入新请求、如何处理不完整工具过程，交给 M3 的上下文选择契约，不因可存储就默认发送。

## 存储与排序的取舍

有序 parts 能保留正文、推理和工具步骤的内部先后关系。直接使用 SDK 格式可避免现在承担字段映射和转换维护成本。自定义格式的自主性有价值，但目前没有足以抵消成本的明确需求。

未来 SDK 发生不兼容变化时，可迁移历史，或保留旧格式定义并在读取时转换。冻结旧格式不等于长期保留完整旧 SDK 依赖，也不保证转换没有成本。工具状态和 Provider 元数据须保真，不能因旧类型无法识别就静默丢弃。

seq 将排序与 UUID 的生成时间解耦。代价是必须定义分配时机及并发合并规则，不能只凭数据库自增列承诺所有客户端到达顺序一致。展示顺序不证明模型看过哪些消息，实际输入仍由运行快照记录。

## 已接受：assistant 首段先入库，再展示

Luke 于 2026-10-24 明确回复“接受‘首段先入库确定位置，再展示’的规则”。阶段 1 assistant 第一个非空正文先成功入库并取得 seq，再发布消息开始及首段正文；之后流式更新、checkpoint、终态及删除不改号。该接受不把后续每个片段都改为先写库再展示，后续仍按 M4 的 checkpoint 策略细化。

代价是 assistant 首段显示增加一次入库等待，换来首次显示时已有确定的历史位置。首段持久化失败按保存故障处理，不因为正文尚未显示而触发 Provider fallback。Provider 首段与浏览器可见首段耗时须区分，具体故障映射和真实时延由 M4/M5 验证。

## 已接受：会话内分配算法与客户端合并

Luke 于 2026-10-24 整体认可 M2 收尾方案，接受以下分配方向。seq 按同会话首次消息入库顺序分配：用户首次保存分配，assistant 沿用上节已接受的时机。以短事务锁定当前会话行，取得锁后读取该会话包含删除占位的最大 seq 并加一，再插入提交，不增加会话计数列。不能裸用 identity 推断提交顺序，所有写入路径与隔离级别须验证。

客户端按稳定消息 ID 合并、按 seq 排序，刷新使用同一规则；收到较大号不表示较小号已收到。服务端确认顺序与各设备感知顺序不完全相同，模型输入仍按每次输入记录追溯。该方案不启用排队、实时订阅或实际工具执行。

锁后以 READ COMMITTED 的独立新查询读最大号、数据库统一强制分配与 seq 不可普通改写，已随 M2 收尾方案接受。具体 SQL、锁顺序与运行验证仍待实施；客户端缓冲/补取细节归 M5，不能将设计接受当作运行通过。比较与官方依据见[seq 分配证据](../plans/stages/stage-1/features/canonical-data-model/evidence/message-seq-allocation.md)，未运行测试。

## 格式版本标识的实施建议

消息行建议增加 `parts_schema_version`，标识 SayHear 读取该行 SDK parts 所遵守的持久化格式契约，首个实际落地格式从 1 起。它是行外元数据，不改变已接受的 AI SDK parts 本身，不建立自有消息内容格式；映射到哪一锁定 SDK 版本在实施时明确，当前不选择或安装版本。

输入记录有独立的 `schema_version`，见 ADR 0010；应用和真实 SDK/适配器包版本另记在运行元数据，不能用某个代码提交号替代数据格式标识。升级代码但持久化格式仍兼容时，不必人为改变格式版本；升级涉及数据解释方式时，必须先决定旧数据如何读，不能仅把旧行的版本号改成新值。

阶段 1 只实现当期实际格式的读写与校验，不预建支持任意未来版本的兼容框架。将来不兼容升级时，再按真实差异选择迁移或读取时转换；保留旧格式读取逻辑不等于长期保留整套旧 SDK。格式变化不得静默丢掉 parts 内容、Provider 元数据或顺序。

引用方案还要求迁移保护旧输入中的消息引用：若 parts 的位置或拼接规则改变，须在同一迁移方案中维护旧记录可解释性，不能让旧引用指向另一段内容。删除后空数组与版本标识可共同保留，仍按已定删除语义不显示原文。

首个格式标识与有限兼容策略已随 M2 收尾方案整体接受，具体列名及 SDK 映射按实施版本落实；未来不兼容升级另按真实需求设计，不将文档存在或版本标识当成兼容性已验证。

## 未定与重评

系统记录已按 ADR 0016 收口，不设独立 system 聊天行；合成工具记录的场景和验收边界见上文。会话最小列已按 ADR 0008 确认，输入快照存 attempt 的 jsonb 列已按 ADR 0010 确认。M2 数据模型、run/attempt 状态集合与输入引用表示已收口，见 ADR 0010 及 M2 收尾规格。终态竞争与 checkpoint 归 M4，客户端补取归 M5，删除生效顺序归 M7，排队范围仍未决定；当前生成中只使用停止，不新增删除入口。本 ADR 不授权实现队列，也不采用旧草案的 tool_call/tool_result 独立行约束。

阶段 1 仍关闭 reasoning，不记录异常返回的思考原文。长期开启 reasoning 时，需要保存 Provider 实际提供的推理内容并支持检查；原文、摘要、加密块与签名的具体契约届时核实。reasoning 与工具调用是独立能力，不互为启用前提。

SDK 格式无法表达明确产品需求、多个运行 SDK 共存、实际迁移成本上升，或观测维护成本明显增加时重评。
