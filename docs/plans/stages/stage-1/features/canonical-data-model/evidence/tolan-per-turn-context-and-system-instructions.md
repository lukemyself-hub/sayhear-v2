# Tolan 每轮上下文与系统指令

核查日期：2026-10-24。问题来自 Luke：Tolan 的每轮重建是否意味着每次都携带 system prompt，能否让回答更贴近产品预期和规则。调查止于澄清公开机制、证据边界及对当前系统记录讨论的影响，不重做框架比较，不运行模型实验。

## 一手来源与能确认的内容

1. [OpenAI 的 Tolan 客户案例](https://openai.com/index/tolan/)，“Context engineering as product engineering”一节。页面标注 2026-02-12。案例明确说每轮都从头重建上下文，重新放入核心人格、语气指导、近期对话及相关长期记忆；并结合情绪、关系与时间调整。可确认每轮重新提供人格与指导内容。没有公开完整请求体、system/developer 消息映射或产品源码，不能声称已证明每条 API 请求中存在某个具体 role。属于供应商发布的团队案例，不是独立因果实验。
2. [DeepSeek 多轮对话指南](https://api-docs.deepseek.com/guides/multi_round_chat)。官方说明 Chat Completion API 无状态，需要在每次请求中提交所需历史。其示例未展示系统消息；本来源只证明不能依赖上一请求自动保留历史，不证明 Tolan 的具体实现。
3. [DeepSeek Chat Completion 接口](https://api-docs.deepseek.com/api/create-chat-completion)。messages 为组成对话的消息列表，支持 system、user、assistant、tool 等角色。这里仅核查系统角色的表达能力，不据此接受 SayHear 的持久化角色方案。
4. [Anthropic 上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。讨论每轮提供哪些上下文、明确系统指令、相关信息筛选，以及上下文变长时的注意力与质量问题。支持把指令设计与上下文筛选一起考虑，不能推出每轮原样重复一段提示便保证遵循规则。
5. [OpenAI 提示工程指南](https://developers.openai.com/api/docs/guides/prompt-engineering)。介绍高优先级指令、明确身份和规则、示例及持续评测。仅作为一般指令机制的官方资料，不能推定不同 Provider 拥有相同的角色优先级或遵循效果。

## 对当前讨论的解释

“每条消息都带 system prompt”容易混淆三个单位：用户发送的一条消息、一次独立模型请求，以及数据库保存的一行记录。

当前推荐每次独立 Provider 请求都明确提供该次运行确定的有效产品指令，再附当前需要的历史与输入。fallback 也要携带必要指令；不依赖上一请求自动记住它们。未来工具多步时逐次核对请求是否保留有效指令，具体接口按锁定 SDK 与 Provider 核实。

这不要求每发一条用户消息就往消息表新增一行相同的 system 记录，也不要求在每条历史 user/assistant 消息前插一份指令。系统记录是否使用 role=system、谁能创建及如何选择，仍属于未决设计。

每次请求有明确且有效的指令，可避免在重新组装或裁剪历史时把规则遗漏。这是推荐的机制理由。内容是否符合预期仍取决于指令清晰度、模型能力、冲突、上下文组织等，效果需用产品行为样本验证，不能承诺每次服从。

稳定规则与每轮动态内容可分开维护：稳定部分包含身份、关系边界与基本回应原则；动态部分包括当前时间、所选历史及后续阶段的记忆。动态数据的存在不应自动给予其修改稳定规则的权限。此为方案建议，不是已接受的数据结构决定。

每次实际发送的系统指令及其余输入，仍按 Issue #1 的实际副本契约进入输入快照。指令权威来源、版本标识、更新时机及存储位置后续决定。
